# Jalon 1 : plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Depuis le panel, sur le Mac de Paul, créer des projets, des environnements et des services à partir d'images publiques. Leur donner des variables et des secrets, les déployer dans le Docker local et voir leurs logs, sur les vraies fondations de Brume.

**Architecture:** Un workspace Rust avec les crates de `archi/base/14-architecture-logicielle.md`. L'engine tient l'état sous forme de log d'événements dans SQLite, avec des cœurs sans I/O. L'agent est seul à parler à Docker (bollard). `brume telemetry` stocke les logs dans DuckDB. `brume api` sert le panel et l'API HTTP. Les services se parlent par des sockets unix. `brume dev` lance tout sur le Mac. Le panel React existant passe des mocks MSW à la vraie API.

**Tech Stack:**
- Rust stable 1.92 : tokio, clap, serde/serde_json, rusqlite (bundled), duckdb (bundled), bollard, axum, secrecy, chacha20poly1305, sha2, uuid v7, time, shell-words, proptest, ts-rs.
- React 19 avec Vite+ (`vp`), TanStack Router, Query et DB, MSW.

**Spec:** [`archi/jalons/2026-10-31-jalon-1-deploiement-local.md`](2026-10-31-jalon-1-deploiement-local.md). Lire aussi `archi/base/13-modele-de-donnees.md`, `14-architecture-logicielle.md`, `18-formats-s3.md` et `front-architecture.md`.

## Global Constraints

- Rust : `#![forbid(unsafe_code)]` dans chaque crate. Style Google Rust, commentaires en anglais, pas de glob import, un module par `use`.
- Formatage : `cargo +nightly fmt` (le `rustfmt.toml` racine contient des options instables). Lint : `cargo clippy --workspace --all-targets -- -D warnings`. Build en stable.
- Crates du cœur (`brume-domain`, `brume-proto`, `brume-engine-core`, `brume-agent-core`) :
  - aucune dépendance à tokio, rusqlite, duckdb, bollard ou axum ;
  - leur `clippy.toml` interdit `std::time::Instant::now`, `std::time::SystemTime::now`, `rand::thread_rng`, `std::collections::HashMap` et `std::collections::HashSet` ;
  - `BTreeMap` et `BTreeSet` partout.
- Seul `brume-agent` dépend de `bollard`, seul `brume-telemetry` de `duckdb`, seul `brume-engine` de `rusqlite`.
- Les secrets ne voyagent que dans `secrecy::SecretString` / `SecretBox`. Une valeur de secret n'entre jamais dans un événement, un segment du bucket, un log `tracing`, une réponse d'API hors `reveal`, ni une ligne de `staged_changes` en clair.
- Toute config générée est sérialisée, jamais construite par concaténation de chaînes.
- Toutes les tailles sont bornées :
  - frame de socket : 4 Mio maximum ;
  - body HTTP : 64 Kio ;
  - valeur de variable ou de secret : 32 Kio ;
  - message d'échec renvoyé par l'agent : 1 Kio ;
  - ligne de log : 16 Kio.
- Panel : les règles de `archi/base/front-architecture.md` (couches, lint, React Compiler, pas de `dangerouslySetInnerHTML`, `fetch` seulement dans `src/api/`). Texte de l'interface en anglais.
- Vérification du panel : `./node_modules/.bin/vp fmt --check && ./node_modules/.bin/vp lint && ./node_modules/.bin/tsc --noEmit && ./node_modules/.bin/vp test run && ./node_modules/.bin/knip && ./node_modules/.bin/vp build`, dans `web/`. Le pnpm 10 global ne lance pas le pnpm 12 épinglé : passer par `./node_modules/.bin/`.
- Machine : Mac Apple Silicon, Docker Desktop 29.4. Socket Docker trouvé par bollard (`connect_with_local_defaults`, sinon `~/.docker/run/docker.sock`). Docker 29 exige l'API 1.44 ou plus : utiliser la négociation de version de bollard.
- Builds parallèles : `CARGO_BUILD_JOBS=3` dans chaque piste, pour ne pas saturer les 16 Go de RAM.
- Commits conventionnels du repo (`feat(engine): …`, `feat(web): …`, `test(agent): …`). Jamais de push.
- Après chaque lot qui touche le panel, arrêt : Paul teste avant le lot suivant.

## Review Focus

1. **Docker Desktop arrêté au lancement de `brume dev`, ou pendant qu'il tourne.** Attendu : `brume dev` démarre quand même et l'agent réessaie toutes les 5 s. Le panel répond, et les déploiements restent `building` ou `deploying` jusqu'au retour de Docker ou jusqu'au délai. Aucune panique. → test dans la tâche 8.
2. **Une image qui n'existe pas** (`nginx:does-not-exist`) ou un registry injoignable. Attendu : le déploiement passe `failed` avec le message (borné) de Docker, affiché tel quel. Le container précédent continue de tourner. → tests dans les tâches 4 et 8.
3. **Un container qui s'arrête tout de suite** (commande invalide), ou un container actif qui plante plus tard. Attendu :
   - pendant un déploiement, il échoue et l'ancien container reste ;
   - un container actif qui plante est relancé par l'agent, avec un délai croissant (1 s, 2 s, 4 s… jusqu'à 60 s), et le service passe `crashed` tant qu'il ne tourne pas.

   → tests dans les tâches 4, 6 et 8.
4. **L'engine redémarre en plein déploiement.** Attendu : le `World` rejoué reprend l'opération à son étape (job de résolution renvoyé, échéance recalculée), et l'agent garde les containers en place. → tests dans les tâches 3 et 4.
5. **Valeurs avec caractères spéciaux** : retour à la ligne, `=`, guillemets, emoji, 32 Kio exactement. Attendu : injectées octet pour octet dans l'environnement du container. Au-delà de 32 Kio ou avec un octet NUL : refusées avec un message clair. → tests dans les tâches 2 et 8.

`Event` : `#[serde(tag = "type")]`, une variante par fait. `EventEnvelope { seq: u64, generation: u32, stream: String, schema_version: u16, at: Timestamp, actor: String, correlation_id: Option<String>, causation_id: Option<String>, prev_hash: String, #[serde(flatten)] event: Event }`.
- `stream` vaut `"<kind>:<id>"`, par exemple `"service:0193…"`.
- `actor` vaut `"admin:<AdminId>"`, `"agent:<MachineId>"` ou `"engine"`.
- `schema_version` vaut 1 partout.

Les variantes d'`Event` :
- `MachineRegistered`, `AdminCreated { admin, identity: BlobId }` ;
- `ProjectCreated`, `EnvironmentCreated`, `ServiceCreated { …, spec }`, `ServiceDeleted` ;
- `ServiceSpecChanged { service, spec }`, `ServiceEgressChanged { service, egress }` ;
- `SharedVariableSet { variable, owner, name, value: SharedValue }`, `SharedVariableRemoved { variable }`, `SecretVersionAdded { variable, version }` (pour un secret de service, en plus de `ServiceSpecChanged`) ;
- `DeploymentRequested { deployment, service, revision: RevisionPlan, reason, author }`, avec `RevisionPlan = Existing(RevisionId) | Resolve(ImageRef) | Reuse { digest, volumes }` ;
- `RevisionCreated { revision, service, number, spec }`, `DeploymentStarted { deployment, revision, secrets }` ;
- `DeploymentHealthy`, `DeploymentSucceeded`, `DeploymentFailed { deployment, reason }` ;
- les événements d'audit, qui ne modifient pas le `World`.

Règles de `decide` (chaque refus est un `Rejection { kind: NotFound | Invalid | Conflict, message }`, message en anglais pour le panel) :
- le nom d'un environnement est unique dans le projet, le slug d'un service unique dans l'environnement ;
- un nom est soit une variable simple ou de build, soit un secret, dans tout le projet (projet, ses environnements, leurs services) ;
- un seul déploiement en cours par service, sinon `Conflict("A deployment is already in progress for <slug>.")` ;
- `Redeploy` exige un déploiement actif et reprend sa révision (`RevisionPlan::Existing`) ;
- `Rollback` exige une révision cible, et que tous ses secrets se résolvent, sinon `Conflict` avec les noms manquants. Il remet la spec du service à celle de la révision (`ServiceSpecChanged`) ;
- `DeployChanges` :
  - un changement d'image donne `RevisionPlan::Resolve` ;
  - un autre changement de spec donne `Reuse` avec le digest de la révision active ;
  - un secret ou l'egress seul donne `Existing`, la révision active redéployée ;
- `RemoveSharedVariable` d'un secret encore utilisé par un déploiement actif donne `Conflict("<NAME> is still used by: <slugs>.")` ;
- `DeleteService` d'un service qui a un déploiement en cours fait échouer celui-ci (`FailureReason::Replaced`), puis supprime le service ;
- `ImageResolved` crée la révision (numéro suivant), puis `DeploymentStarted`, avec les secrets résolus à cet instant ; si un secret manque, `DeploymentFailed`.
