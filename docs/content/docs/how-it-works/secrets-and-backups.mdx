Each secret is held by the one component that needs it, and the server keeps no secret it only needed once. Backups are encrypted with a key the server does not have and sent off the server with write-only credentials: the server can write backups, but it can neither read nor delete them.

## Platform secrets

| Secret | Held by | Note |
|---|---|---|
| Secrets master key | `brume engine` | systemd credentials, see [App secrets](#app-secrets) |
| GitHub App private key | `brume engine` | generates one-hour tokens |
| S3 credentials | `brume engine` | write-only |
| age public key | `brume engine` | the private key stays with you |
| Webhook HMAC secret | `brume webhook` | |
| Cloudflare tunnel token | cloudflared | the only Cloudflare token stored |
| Cloudflare API token | nobody | used at install, then forgotten |
| Tailscale auth key | nobody after install | single use |

## App secrets

- **Defined on the project, the environment or the service,** resolved at deploy time, and never copied into a revision. See the [data model](/docs/how-it-works/data-model).
- **Encrypted in the database with the master key.** The gain is limited while the key sits on the same machine: the real protection is for backups.
- **The master key lives in systemd credentials** (`LoadCredentialEncrypted=`, see [systemd credentials](https://systemd.io/CREDENTIALS/)). It is encrypted on disk, and only the engine receives it at startup, in a private directory. Other services cannot read it, even through a bug that lets them read files. This needs Debian 12 or Ubuntu 24.04.
- **Decrypted only by the engine,** and injected when the container is created.
- **The API never sees a secret in clear,** except on an explicit "reveal" action.
- **In the Rust code,** secrets are stored in the types of the `secrecy` crate.
- **Environment variables in 0.1.** The one exception is the MongoDB replica set keyfile, written in the database volume: see [Templates](/docs/use/templates). Secrets as files on tmpfs come later, see the [roadmap](/docs/how-it-works/roadmap).
- **Logs.** Brume masks secrets in build logs. Apps sometimes write secrets to their own logs, so log retention is limited and backups contain no logs.

## Backups

### What is backed up

- **Consistent dumps** (`pg_dump`, `mongodump`, a Redis RDB snapshot, `.backup` for SQLite), never a copy of files that are being written. [Templates](/docs/use/templates) has the details for each database.
- **Brume makes its own dumps:** `pg_dump | age | upload`. It does not use restic, because restic must read, list and delete in its repository, which is incompatible with write-only credentials.
- **Brume's own state** (configuration, encrypted secrets). Without it, nothing can be rebuilt.
- **Not the logs.**

<Callout type="warn" title="The master key is not backed up in 0.1">
  If the server is lost, the encrypted secrets in Brume's state cannot be restored. The [roadmap](/docs/how-it-works/roadmap) covers adding the master key to the encrypted backup.
</Callout>

### Encryption

Backups are encrypted with [age](https://age-encryption.org), with an asymmetric key pair.

- **The server only has the public key.** It can encrypt, not decrypt.
- **You receive the private key at install,** or you supply your own public key. The private key is required to restore.
- **The public key can only be changed on the host,** as root, never from the panel. Otherwise a stolen session could make the next backups readable by the attacker.
- **An attacker who takes the server cannot read past backups,** since the server cannot decrypt them.

### Storage

- **Off the VPS,** on S3-compatible storage that you configure from the panel.
- **Any change of destination triggers an alert.** Otherwise a stolen session could silently send the next backups somewhere else.
- **Write-only credentials** (`PutObject`), with no right to delete.
- **Bucket versioning or Object Lock is required:** `PutObject` can overwrite an existing object whose name is known. Brume does not check this in 0.1, so you must enable it yourself. See the [roadmap](/docs/how-it-works/roadmap).
- **Retention is handled by bucket lifecycle rules,** not by Brume, which cannot delete anything.

### Verification

The server checks each dump before it leaves. Only you can check a full restore, because only you have the private key.

- **The server cannot decrypt its own backups.** So the automatic test restores each dump into a temporary container before encryption, then checks the checksum of the uploaded object.
- **A full restore from S3 needs the private key.** Run one regularly from your own machine.
- **Brume alerts you when a backup fails.** Silent failure is the most common case.

## Audit log

The audit log is sent continuously to S3 with Object Lock. See [Observability](/docs/how-it-works/observability).
