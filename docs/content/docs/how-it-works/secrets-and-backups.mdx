Each secret is held by the one component that needs it, and the server keeps no secret it only needed once. Brume's state and the database backups leave the server for a single S3 bucket. Secrets and backups are encrypted there; the event log is not. Built images stay on the server. The S3 credentials can read and write, but cannot delete, change lifecycle rules or suspend versioning, so a compromised server cannot erase what has already left. Backups are encrypted for your age key, which the server does not have.

## Platform secrets

| Secret | Held by | Note |
|---|---|---|
| Secrets master key | `brume engine` | systemd credentials, see [App secrets](#app-secrets). Also saved on S3, encrypted for your age keys. |
| GitHub App private key | `brume engine` | One App per installation. Generates one-hour tokens limited to the repository being built: see [Builds and deployments](/docs/how-it-works/builds-and-deployments#access-to-github). |
| S3 credentials | `brume engine`, `brume agent` | Read and write, with no right to delete, and no rights on lifecycle rules or versioning. |
| age public key | `brume engine` | The private key stays with you. |
| Webhook HMAC secret | `brume webhook` | Saved in the state, on S3. |
| Cloudflare tunnel secret | cloudflared | Lets whoever holds it run a connector of the tunnel: the engine detects unknown connectors. |
| Read-only Cloudflare token | `brume engine` | Tunnel and DNS, to alert on an unknown connector or DNS record. |
| Cloudflare API token | nobody | Used at install, then forgotten. |
| Tailscale auth key | nobody after install | Single use. |

The Cloudflare and Tailscale rows apply only in the recommended modes, Cloudflare Tunnel for public traffic and Tailscale for administration. See [Networking](/docs/how-it-works/networking).

## App secrets

- **Defined on the project, the environment or the service,** resolved at deploy time, and never copied into a revision. See the [data model](/docs/how-it-works/data-model).
- **Encrypted in the database with the master key.** The gain is limited while the key sits on the same machine: the real protection is for backups.
- **The master key lives in systemd credentials** (`LoadCredentialEncrypted=`, see [systemd credentials](https://systemd.io/CREDENTIALS/)). It is encrypted on disk, and only the engine receives it at startup, in a private directory. Other services cannot read it, even through a bug that lets them read files. This needs at least Debian 12 or Ubuntu 24.04, which every supported system meets: see [Host and installation](/docs/how-it-works/host-and-installation#requirements).
- **The master key is also saved on S3,** encrypted for your age keys. See [The master key and your age keys](#the-master-key-and-your-age-keys).
- **Decrypted only by the engine,** then passed to the agent, which injects them when it creates the container.
- **The API never sees a secret in clear,** except on an explicit "reveal" action.
- **In the Rust code,** secrets are stored in the types of the `secrecy` crate.
- **Environment variables in 0.1.** The one exception is the MongoDB replica set keyfile, written in the database volume: see [Templates](/docs/use/templates). Secrets as files on tmpfs come later, see the [roadmap](/docs/how-it-works/roadmap).
- **Logs.** Brume masks secrets in build logs. Apps sometimes write secrets to their own logs, so log retention is limited and backups contain no logs.

## Backups

### What is backed up

- **Consistent dumps** (`pg_dump`, `mongodump`, a Redis RDB snapshot, `.backup` for SQLite), never a copy of files that are being written. [Templates](/docs/use/templates) has the details for each database.
- **Brume makes its own dumps:** `pg_dump | age | upload`. It does not use restic, because restic must read, list and delete in its repository, which is incompatible with credentials that cannot delete.
- **Brume's own state** goes to S3 continuously, as its event log. See [State on S3](#state-on-s3).
- **The master key,** encrypted for your age keys: a lost server can be rebuilt with your age private key.
- **Not the logs.**

### Encryption

Backups are encrypted with [age](https://age-encryption.org), with an asymmetric key pair.

- **The server only has the public key.** It can encrypt, not decrypt.
- **You receive the private key at install,** or you supply your own public key. The private key is required to restore, the state as well as the backups. Several recipients are advised, and you prove you kept your key before the install ends: see [The master key and your age keys](#the-master-key-and-your-age-keys).
- **The public key can only be changed on the host,** as root, never from the panel. Otherwise a stolen session could make the next backups readable by the attacker.
- **An attacker who takes the server cannot read past backups,** since the server cannot decrypt them.

### Storage

- **Off the VPS,** on S3-compatible storage. A single bucket receives the state and the backups: see [What goes to the bucket](#what-goes-to-the-bucket).
- **Required at install, and changeable only on the host,** as root, never from the panel. A stolen session cannot send the next backups somewhere else.
- **Any change of bucket triggers an alert.** A new bucket or folder receives the whole log again, sent from SQLite, with its blobs and a new copy of the master key. The backups already sent stay in the old one.
- **Read and write credentials, with no right to delete, to change lifecycle rules or to suspend versioning.** A credential that can set a lifecycle rule or suspend versioning can erase everything in a day, without ever deleting an object. `brume install` checks that these three operations fail, and refuses the credential otherwise.
- **Reading reveals no secret.** Blobs are encrypted, and backups are encrypted for a key the server does not have. The event log, in clear, shows the structure of your setup.
- **It can abort an upload in several parts.** That right touches no object already stored.
- **One credential, shared by the engine and the agent.** Brume can never delete anything on S3.
- **A bucket at another provider than your VPS is advised,** with an account protected by hardware 2FA. Whoever holds that account can delete the bucket, whatever the rights of the credential.
- **Bucket versioning or Object Lock is required:** `PutObject` can overwrite an existing object whose name is known. Brume writes with `If-None-Match`, and [`brume verify`](#brume-verify) checks versioning or Object Lock. Versioning keeps the original of an overwritten object, to recover by hand.
- **Retention is handled by bucket lifecycle rules,** not by Brume, which cannot delete anything. Only backups expire.
- **The log, the blobs and the keys never expire.** No lifecycle rule must target `log/`, `blobs/` or `keys/`: a blob still in use, written two years ago, looks like a purged blob. Together they weigh a few MB.

### Verification

The server checks each dump before it leaves. Only you can check a full restore, because only you have the private key.

- **The server cannot decrypt its own backups.** So the automatic test restores each dump into a temporary container before encryption, then checks the checksum of the uploaded object.
- **A full restore from S3 needs the private key.** Run one regularly from your own machine, with [`brume verify`](#brume-verify).
- **Brume alerts you when a backup fails.** Silent failure is the most common case.

## State on S3

The VPS is disposable. Brume's state and the database dumps live in the bucket. A new VPS can be rebuilt from it, and rebuilds the images from their commits.

- **SQLite is authoritative while Brume runs, S3 once the disk is lost.** SQLite holds everything, since the control state weighs a few MB. Brume never fetches from S3 data missing locally.
- **Uploads to S3 are always asynchronous,** never on the path of a command. An S3 outage blocks neither commands, nor deployments, nor webhooks.
- **The price: the last second of state** can be lost if the VPS disappears.
- **App data is on S3 only as dumps.** A restore brings each database back to its last dump. Volumes outside the [templates](/docs/use/templates) are not backed up in 0.1.

### What goes to the bucket

One bucket, with versioning or Object Lock:

```text
log/<generation>/<seq>.seg    event segments
blobs/<id>                    values of variables and secrets, platform secrets
keys/master.<n>.age           master key, encrypted for your age keys
backups/…                     database dumps
```

- **Platform secrets that must survive a restore are blobs:** the GitHub App private key and the webhook HMAC secret. Your identity allowlist and your passkeys are in the log.
- **Kept off S3:** sessions, telemetry and app logs, the build cache, the observed state, built images, static site archives, and images pulled from a registry.
- **Built images and static site archives are not copied.** Brume is not a registry: they live only in the local dockerd, which keeps those of the last 10 revisions (see the [data model](/docs/how-it-works/data-model)). A restore rebuilds them from their commits.
- **Images pulled from a registry are not copied.** A restore pulls them again by their digest. If the registry deleted them or cannot be reached, the service does not restart. See [Accepted risks](#accepted-risks).
- **The object format is documented,** never an internal Rust format: names and formats are specified so that another tool can read the bucket. An object written to S3 never changes, so every format stays readable by every later version of Brume.
- **You can put Brume in a folder of an existing bucket,** empty at install. The folder never enters the encryption, so objects moved to another bucket or folder stay readable.

### State encryption

Only what is sensitive is encrypted.

- **Blobs are encrypted with the master key,** using XChaCha20-Poly1305: the values of variables and secrets, the platform secrets, and emails. Each blob starts with a cleartext header (format version, algorithm, key ID), and its name is part of the authenticated data, so a blob cannot be moved under another name.
- **The event log goes to S3 in clear.** It holds no value and no email: those live in blobs. Whoever reads the bucket sees the structure of your setup: project and service names, domains, repositories.
- **The hash chain protects the log against corruption.** Each event carries the hash of the previous one, so a corrupted, missing or modified segment shows. It does not stop someone holding the S3 credential, who can recompute it: see [Accepted risks](#accepted-risks).
- **The agent receives no key derived from the master key.** It only uploads backups, encrypted with age.
- **Backups stay encrypted with age,** for your keys. The server cannot read them: see [Encryption](#encryption).
- **The hashes of backups are in the log.** A restore checks each dump against its hash.

### The master key and your age keys

- **The master key is stored on S3, encrypted with age** for each of your public keys. Recipients are changed on the host. Each change writes a new `keys/master.<n>.age` object.
- **The install advises several recipients,** for example a paper key and a YubiKey (`age-plugin-yubikey`).
- **You prove you kept your key before the install ends.** Brume encrypts a code for each public key, and you decrypt it on your machine and type it back.
- **The panel regularly reminds you to run a restore drill** with [`brume verify`](#brume-verify).
- **Master key rotation comes later.** Thanks to the key ID, old blobs will stay readable with the old key. Rotation will not protect blobs already sent.

<Callout type="warn" title="Your age private key is the one thing to keep off the server">
  If you lose it, neither the secrets nor the backups can be restored. Keep several recipients, and run `brume verify` from your machine to check that your key still opens the bucket.
</Callout>

### Upload

- **An engine subscriber reads the log** from its checkpoint, groups at most one second of events into a segment and uploads it. The blobs it references go first.
- **Each segment starts right after the previous one,** and is named after the position of its first event.
- **Written with `If-None-Match: *` and a checksum.** An existing object is never overwritten.
- **If the response is lost,** the engine reads the segment back and compares it with its own. If they match, the upload succeeded. If they differ, someone else wrote under that name: see the next section.
- **The upload lag is measured.** Beyond 5 minutes, an alert goes out, and the panel shows the time of the last upload.
- **The agent uploads the backups.** A large dump goes up in several parts (multipart upload), since a single upload is limited to 5 GB at most providers. `If-None-Match` then applies to the call that assembles the parts.
- **Brume aborts an interrupted upload in several parts.** The parts of an unfinished upload are billed without being visible, so `brume install` also advises a bucket rule that cleans up unfinished uploads after 7 days.

### Two servers on one bucket

- **Contiguous segments make detection reliable.** Two servers that diverge always write the same segment name at their first divergent write, and the second one gets a 412 error.
- **The loser goes read-only:** it refuses commands, stops uploading and sends an alert.
- **An object dropped under the next name by someone else** has the same effect. You then change the credential, then the bucket or folder: see [Storage](#storage).
- **Limit:** a server that no longer writes anything never finds out. Its apps keep running, but without public traffic: see [Restore](#restore).
- **Not every provider supports `If-None-Match`.** Brume tests it when you configure the bucket, and warns you if this detection cannot work.

### Restore

`brume restore` runs the steps of `brume install` ([Host and installation](/docs/how-it-works/host-and-installation)), except the creation of the keys, then:

1. **You give the bucket credentials and your age private key.** You type the key, and Brume keeps it in memory for the duration of the restore, never on disk.
2. **Brume decrypts the master key** (`keys/`) and stores it in the systemd credentials of the new host.
3. **It downloads the current generation of the log** and checks the hash chain, then rebuilds SQLite: log, blobs, indexes. An unreadable segment stops the restore at the last valid event, and you are told. A missing blob is listed, so that you enter its value again. See [Reading the bucket](#reading-the-bucket).
4. **It sets up ingress and administration again,** in the modes you choose:
   - with Cloudflare, it creates a new tunnel and repoints the wildcard CNAME, as at install, so the old server no longer receives public traffic if it comes back;
   - in direct ingress, you repoint the DNS to the new IP yourself;
   - with Tailscale, the new server joins the tailnet as a new device, and you remove the old one.
5. **It rebuilds the images and static sites of the revisions in service from their commits.** Each build creates a new revision, with the commit and the variables of the revision in service: the image can differ from the old one. An image pulled from a registry is pulled again by its digest. Older revisions stay in the history, but can no longer be rolled back.
6. **It restores the last dump of each database,** decrypted with your age key. For each database, it shows the gap between the time of the dump and the end of the log. It offers to put the services that use the database back on the revision that ran at the time of the dump: otherwise newer code may expect a schema the restored database does not have.
7. **It starts the services.** The agent brings Docker to the desired state, and the engine resumes uploading right after the last segment. If the restore stopped on an unreadable segment, it opens a new generation of the log, since the next name is taken.

- **You sign in to the panel again:** sessions do not survive a restore. Your allowlist and your passkeys are in the state.
- **Restore is tested every night on a real VM:** install, write, wipe the disk, restore.

### `brume verify`

`brume verify` is the only way to know, before you need it, that the bucket can be restored. It detects a bad lifecycle rule, a missing Object Lock or a lost key.

- **It runs from your own machine,** with read credentials and your age private key. It writes nothing.
- **It checks that:**
  - each segment reads and the hash chain is complete, from one generation to the next;
  - a restore rebuilds a valid state;
  - each blob decrypts;
  - each backup decrypts and matches the hash recorded in the log;
  - no lifecycle rule targets `log/`, `blobs/` or `keys/`, if its credentials can read those rules.

### Reading the bucket

These rules apply to `brume restore`, to `brume verify`, and to the engine when it checks a doubtful upload.

- **Brume reads the current version of each object.** It never writes twice under the same name. Bucket versioning keeps the original of an overwritten object, to recover by hand.
- **It follows the expected names, never the bucket listing.** Each segment starts right after the previous one.
- **A restore reads only the last generation of the log,** whose first event holds the whole state. `brume verify` reads every generation, and checks that each one links to the previous through the hash chain.
- **Reading stops at the first unreadable segment:** it does not parse, its header line does not match its name, or it breaks the hash chain. A restore resumes from the last valid event, and tells you.
- **A missing blob, or one that does not decrypt, does not stop a restore.** The value is missing, and the restore lists the variables and secrets to enter again.

### What a purge does not reach

- **A purge does not reach S3.** Purged blobs stay there forever, encrypted with the master key, as backups already do. See the [data model](/docs/how-it-works/data-model) for purges.
- **A leaked secret is revoked at its issuer:** erasing it is not enough.

### Accepted risks

| Risk | Why Brume accepts it |
|---|---|
| The last second of state is lost with the VPS. | In exchange, an S3 outage blocks nothing. |
| A restore replays the whole log, including events written by an attacker who had root. There is no restore to a point in time and no master key rotation. | 0.1 focuses on prevention and detection. Restoring to a point in time comes later: see the [roadmap](/docs/how-it-works/roadmap). |
| An image pulled from a registry is not on S3. If the registry deleted it or cannot be reached, a restore does not start the service. | Copying it would double the storage of an image its registry already keeps. |
| An old VPS that comes back keeps its apps running, without public traffic. Their background jobs (crons, queues) can still write elsewhere. | It is rare, and the new tunnel cuts the public traffic. |
| The engine is a single point of failure. Without it, the apps run, but nothing deploys. | Automatic failover would need consensus, not just S3. |
| An attacker with root can erase the second not uploaded yet and stop the upload. The alert would come from the server they control. | What has already been uploaded stays intact. An external alert comes later: see the [roadmap](/docs/how-it-works/roadmap). |
| S3 providers do not all support the same features (`If-None-Match`, including when assembling an upload in several parts, Object Lock). | Brume tests the bucket when you configure it. The egress cost depends on the provider. |
| A restore rebuilds every running service: it takes longer, and the image can differ from the old one. Older revisions can no longer be rolled back. If the commit is gone from GitHub (deleted branch, rewritten history), the service does not restart. | Brume is not a registry. Copying built images to S3 comes later: see the [roadmap](/docs/how-it-works/roadmap). |
| The log is not authenticated. Whoever holds the S3 credential can write fake events, recomputing the hash chain: add their identity to the allowlist, change a service's image. A restore would replay them. They can also block uploads by dropping an object under the next name. | The credential lives on the server, and the provider account is protected by hardware 2FA. Authenticated events come later: see the [roadmap](/docs/how-it-works/roadmap). |
| Whoever reads the bucket sees the structure of your setup: project and service names, domains, repositories. | These names grant no access. Values and emails are in blobs, encrypted. |

## Audit log

The audit log is Brume's event log, sent continuously to S3, in clear and hash-chained. See [Observability](/docs/how-it-works/observability#audit-log) and [Upload](#upload).
