Brume configures the whole server itself, starting from a fresh VPS. A tiny script downloads and verifies the `brume` binary, then `brume install` does the rest: ingress and administration modes, firewall, Docker, Tailscale and Cloudflare Tunnel if you use them, encryption keys, the S3 bucket, systemd services and automatic updates. All of that host configuration lives in the Rust binary, not in bash: it can be tested, replayed safely, and reapplied at every update.

## Requirements

- **A fresh VPS.** On an existing server, ports already published and services already exposed would stay open.
- **Debian 12 or 13, or Ubuntu 24.04 or 26.04,** on amd64 or arm64. systemd credentials need at least Debian 12 or Ubuntu 24.04. The Red Hat family (Alma, Rocky, RHEL) comes later, because it uses SELinux instead of AppArmor and dnf instead of apt: see the [roadmap](/docs/how-it-works/roadmap).
- **Docker 28.5.2 or later.** [Networking](/docs/how-it-works/networking) explains why.
- **An S3-compatible bucket,** with versioning or Object Lock, and credentials that can read and write but cannot delete, change lifecycle rules or suspend versioning. Brume can live in a folder of an existing bucket. `brume install` checks this. See [Secrets and backups](/docs/how-it-works/secrets-and-backups#storage).
- **In the recommended modes:** a domain on Cloudflare DNS and a tailnet. See [Networking](/docs/how-it-works/networking).

## The install script

The install command downloads `install.sh` from GitHub Releases and runs it:

```bash
curl -sSL https://github.com/brumecloud/brume/releases/latest/download/install.sh | bash
```

- **Tiny, readable in 30 seconds** before you run it: download, verify, run `brume install`.
- **Wrapped in a function called on the last line,** so nothing runs partially if the connection drops.
- **Served by GitHub Releases, like the binaries.** The script decides what to download and whether to verify it, so it comes from the same place as the binaries.
- **Verifies the [minisign](https://jedisct1.github.io/minisign/) signature of the binary.** Versions are pinned.
- **Manual verification is documented.** The minisign public key is published in the README and on brume.dev, so you can check `install.sh` and the binary before running them. To fool this check, an attacker has to compromise both.
- **Still open: a verification channel outside GitHub.** brume.dev is deployed from the same GitHub repository, so a compromised GitHub account reaches both. See the [open decisions](/docs/how-it-works/roadmap#open-decisions).

<Callout type="warn" title="The first install trusts GitHub">
  A compromised GitHub account can change `install.sh` so that it skips the verification. The offline signing key only protects updates. To close this gap on your server, verify `install.sh` and the binary by hand before running them.
</Callout>

## What `brume install` does

The steps run in this order:

1. Choose the ingress and administration modes. Cloudflare Tunnel and Tailscale are recommended. The other modes are direct ingress for public traffic, and an SSH tunnel or a public panel for administration. You choose them on the host, like every dangerous option, and the panel always shows when a mode that is not recommended is active. See [Networking](/docs/how-it-works/networking).
2. Install Brume's nftables table, with the systemd unit that loads it before Docker. See [Networking](/docs/how-it-works/networking).
3. Install Docker from the official apt repository, signed with GPG (not through a second `curl | sh`), and write `daemon.json`.
4. With Tailscale: join the tailnet with a single-use auth key, pre-authorized and tagged `tag:brume`.
5. Create the admin account: your Tailscale login for the identity allowlist, or a password without Tailscale.
6. With Cloudflare: create the tunnel, its local configuration and the wildcard CNAME, and turn on HSTS and the redirect to HTTPS, with an API token, then forget that token. Then ask for a second, read-only token (tunnel and DNS), which the engine keeps to detect an unknown tunnel connector or DNS record. In direct ingress, you point the DNS to the server's IP yourself.
7. Generate the age key pair and show the private key once, or import your own public keys. Several recipients are advised. You decrypt a code to prove you kept your key.
8. Configure the S3 bucket, and its optional folder, which must be empty, and test it: write, read, and `If-None-Match`, including when assembling an upload in several parts. Then check that a delete, a lifecycle rule and a versioning suspension all fail. A credential that succeeds at any of these three is refused. Advise a bucket rule that cleans up unfinished uploads after 7 days. [Secrets and backups](/docs/how-it-works/secrets-and-backups#storage) explains why.
9. Create the system users (including `brume-agent`), the systemd units and the master key (systemd credentials). Store the master key on S3, encrypted for your age keys, then start the services.
10. Lock down SSH. With Tailscale: enable Tailscale SSH and check that it works. Only then: key-only SSH, port 22 closed to the public, and UFW closed to inbound traffic except from the `ingress` network to the webhook. Without Tailscale: key-only SSH on port 22, the only open port, along with 80 and 443 in direct ingress.
11. Configure `unattended-upgrades`: the distribution, Docker and Tailscale repositories, the Docker major version pinned, automatic reboot. See [Updates](#updates).
12. Show the enrollment URL for the second factor, single use and valid for 15 minutes. The [admin panel](/docs/how-it-works/admin-panel) page covers the second factor.

At the first launch of the panel, you create the installation's GitHub App: see [Builds and deployments](/docs/how-it-works/builds-and-deployments#access-to-github).

## Docker

- **`daemon.json`** sets `no-new-privileges: true`, `live-restore: true`, and log rotation for the default driver and for the local copy. Without a limit, Docker logs fill the disk, and SQLite and Brume go down.
- **`userns-remap: "default"`** from install. See [Runtime](/docs/how-it-works/runtime).
- **`default-address-pools` pinned,** outside the hosting provider's private network, so the nftables rules know the Docker subnets.
- **On Ubuntu, `kernel.apparmor_restrict_unprivileged_userns=0`,** for the whole host: the builder needs unprivileged user namespaces. Debian needs no change. This is still to confirm on Ubuntu 26.04 and Debian 13. See [Builds and deployments](/docs/how-it-works/builds-and-deployments).
- **The Docker API never listens on TCP** (port 2375). It is the classic way in for cryptominers.
- **Default seccomp and AppArmor profiles.**

## SSH

- **Key authentication only.**
- **With Tailscale, Tailscale SSH,** with port 22 closed to the public. Without Tailscale, SSH stays open on port 22, by key only.
- **Fallback:** the hosting provider's console.

## systemd services

- **One dedicated user per service,** with the hardening described in [Architecture](/docs/how-it-works/architecture).
- **Brume's files are `0600`,** owned by their service.
- **OOM priority:** Brume and Traefik get priority protection from the OOM killer.
- **`systemd-analyze security` in CI** comes later.

## Updates

Each layer has its own update path: Brume updates itself through a signed manifest and its updater, its components come with each Brume release, and the OS, Docker and Tailscale update through `unattended-upgrades`.

### Brume

- **Brume updates itself.** The engine reads `https://brume.dev/latest.json` at regular intervals. This file is the manifest of the latest release, signed offline with minisign: the version of its own format, the release version, an expiry date, whether the release compacts the log, and the hash and GitHub Releases URL of the binary. The format version lets the first binary's parser cleanly refuse a format it does not know. See [Development](/docs/customize/development#signing-with-minisign).
- **Signature checked before anything is read.** The engine checks the signature on the raw bytes, before it parses the JSON, as the webhook checks its HMAC: it parses no unsigned data from the internet.
- **The updater does not trust the engine.** The engine starts it when a newer version exists, and the updater redoes every check: the signature with one of the two public keys built into the binary already installed, the version, the compaction flag and the hash of the downloaded binary. Then it replaces the binary and restarts the services.
- **Two public keys from v0.1:** the signing key, and a backup key kept offline elsewhere. If the first is lost or stolen, a release signed with the backup key replaces it. A key added later would not protect the servers still on older versions.
- **An expired manifest triggers an alert.** brume.dev is hosted on Vercel and deployed from the same GitHub repository. It can freeze updates by always serving the same file, but it cannot make Brume install a fake version or an old one. The expiry date detects a freeze, so the maintainer re-signs `latest.json` regularly, even without a release.
- **No downgrade.** The signed manifest carries the version, and the updater refuses any version lower than or equal to the installed one. An old, vulnerable version stays signed: without this check, an attacker could reinstall it.
- **A release that compacts the log cannot be skipped.** Its signed manifest says so, and the updater installs it before any newer release. Otherwise an install still on the old log generation could no longer read its log.
- **Components** (Traefik, Caddy, cloudflared, BuildKit) are pinned by digest and updated with every Brume release. A year after install, the main risk would be an unpatched component.
- **To decide before the first release:** when updates install (the proposal is the 4 a.m. reboot window), a local fallback to the previous binary if the new one does not start, and a progressive rollout through a percentage in `latest.json`. See the [open decisions](/docs/how-it-works/roadmap#open-decisions).

### OS, Docker and Tailscale

- **`unattended-upgrades`,** configured with the distribution, Docker and Tailscale repositories. By default, it only follows the distribution's.
- **Docker major version pinned** by Brume (apt preferences), and raised at each Brume release, after testing. Patch versions install on their own. A major version can break a Docker API client: Docker 29 raised its minimum API version.
- **Automatic reboot** when an update needs one, a kernel update in particular: without a reboot, a patched kernel does not apply. The reboot happens at 4 a.m. server time, which you can change on the host. At boot, the nftables table loads before Docker, then the agent restarts all containers. Apps are down during the reboot.
- **The agent waits for the engine at boot** before it starts the containers, in 0.1. Starting the apps without the engine comes later: see the [roadmap](/docs/how-it-works/roadmap).
- **dockerd updates:** with `live-restore`, containers keep running during a patch update. A major version restarts them.
- **tailscaled updates,** with Tailscale: the panel and SSH drop for a few seconds.
- **Alerts** for a failed update, a reboot and an expired update manifest. See [Observability](/docs/how-it-works/observability#alerts).

### Telemetry and the update check

The update check is the only telemetry Brume sends to the Brume project.

- **What the project learns.** When the engine reads `latest.json`, the project learns the server's IP and the installed version: enough to count installs per version.
- **What the check sends:** only the version, the OS and the architecture. No domain, no account, no installation ID, so the count stays approximate.
- **Announced at install and in these docs.**
- **Short log retention on brume.dev,** because an IP address is personal data under the GDPR.
- **You can turn the check off on the host,** as root. Brume updates then become manual.
- **Brume's own telemetry stays with you.** Its traces, metrics and logs stay on your server, or go to your own backend: see [Observability](/docs/how-it-works/observability).

## Restore and verify

- **`brume restore`** rebuilds a lost server from the bucket. It runs the steps of `brume install`, except the creation of the keys, with your age private key.
- **`brume verify`** checks, from your own machine, that the bucket can be restored.
- See [Secrets and backups](/docs/how-it-works/secrets-and-backups#restore).

## Emergency access

If Tailscale or the panel is unreachable, you still have the hosting provider's console and the local `brume` CLI, through a unix socket in `0600`. The CLI manages the identity allowlist and resets the second factor.
