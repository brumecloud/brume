A push to a configured branch starts a build. Each step runs in its own component, with only what it needs: the webhook checks the request and queues a build, the engine decides, the agent starts the builder, and the builder clones and builds the image without touching the runtime. The agent then loads the image, and the engine deploys it by digest.

## The flow

1. A push to a configured branch triggers a GitHub webhook.
2. The request goes through Cloudflare, then cloudflared, then Traefik (GitHub IPs only, rate limit), then `brume webhook`. In direct ingress, without Cloudflare, the request reaches Traefik directly: see [Networking](/docs/how-it-works/networking#traefik).
3. `brume webhook` checks the signature and calls `enqueue_build(repo_id, ref)` on the engine.
4. The engine checks that the ref matches the configured branch, then asks the agent for the build.
5. The agent starts the builder, which clones the repository and builds the image with [Railpack](https://railpack.com).
6. The agent loads the image into dockerd and uploads it to S3. The engine creates the revision, then deploys it by digest.

## Three sources

- **A push to a configured branch,** through the GitHub App: the flow above.
- **A `brume deploy` from a folder:** its current commit, already pushed to GitHub, built through the same flow, without a webhook. See [CLI and AI agents](/docs/how-it-works/cli-and-ai-agents#deploying-a-folder).
- **An image from a registry:** no build. The tag is resolved to a digest at deployment, see [Runtime](/docs/how-it-works/runtime).

All three end the same way: a revision that points to a digest, then a deployment.

## The webhook

The webhook receives requests from the internet, so it treats the payload as a trigger and nothing more.

- **A separate process, with its own listener,** never a route of the admin API. [Architecture](/docs/how-it-works/architecture) explains why.
- **Only GitHub's IP ranges reach it,** in every mode: Traefik filters them, with a rate limit. Every GitHub user shares these ranges, so the signature check below remains the real barrier. See [Networking](/docs/how-it-works/networking#traefik).
- **HMAC signature `X-Hub-Signature-256`,** checked in constant time, before the JSON is parsed. See GitHub's guide to [validating webhook deliveries](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries).
- **Limited body size.**
- **Replay protection.** GitHub does not sign a timestamp, so the webhook ignores duplicate `X-GitHub-Delivery` IDs.
- **The payload is only a trigger.** The repository comes from Brume's configuration, and the ref must match the configured branch.
- **Pushes to configured branches only.** There are no pull request previews in 0.1. When they arrive, a pull request from a fork is never built with secrets.
- **No outbound network.**

## Access to GitHub

Brume reads your code through a GitHub App that belongs to your installation alone, with read-only rights and short-lived tokens.

- **One GitHub App per Brume installation, rather than a personal token.** You create it from the panel at first launch, with GitHub's [manifest flow](https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-from-a-manifest). The panel sends your browser to GitHub with a manifest: the App's name, the webhook URL of this installation, its permissions and the `push` event. You confirm, and GitHub sends your browser back to the panel with a code. The engine exchanges that code for the App's ID, its private key and the webhook secret.
- **The flow works with a panel reachable only through the tailnet,** because the return trip goes through your browser, not from GitHub to the server.
- **No App shared by the Brume project.** A shared App would force a single webhook URL, so a central relay, and one private key common to every installation.
- **Read-only.** The App has the `contents: read` and `metadata: read` permissions, and is installed only on the repositories you pick.
- **One token per build, limited to the repository being built.** The token has `contents: read` and expires after one hour. The engine generates it with the App's private key, and the agent passes it to the builder. A malicious dependency that steals it can read only that repository, for one hour.
- **The token must never end up in the image.** A clone through `https://x-access-token:TOKEN@github.com/...` writes the token into `.git/config`, and a `COPY . .` then puts it in an image layer. So the token goes through a credential helper or a header, and `.git` is excluded from the build context.
- **The clone happens in the builder, never in the engine or the agent.** Git has had code execution flaws triggered by cloning a crafted repository, such as [CVE-2024-32002](https://www.cve.org/CVERecord?id=CVE-2024-32002).
- **`GIT_ALLOW_PROTOCOL=https:ssh`,** and no arbitrary submodules.
- **`--` before any user argument** passed to `git`, so that a ref starting with `-` cannot become an option.

## The builder

The builder runs BuildKit rootless in its own container, started by the agent. Its sandbox is weaker than an app's. Brume accepts this because the code it builds is trusted, dependencies included: see the [threat model](/docs/how-it-works/threat-model).

### Sandbox

- **BuildKit rootless, in its own container started by the agent,** with no Docker socket.
- **A weakened sandbox, by necessity.** Inside a container, rootless BuildKit needs seccomp, AppArmor and `systempaths` set to `unconfined`. According to the [BuildKit documentation](https://github.com/moby/buildkit/blob/master/docs/rootless.md), `systempaths=unconfined` can allow reading and writing sensitive kernel files.
- **Unprivileged user namespaces required.** On Ubuntu, `brume install` disables `kernel.apparmor_restrict_unprivileged_userns`, for the whole host. Debian needs no change. This is still to be confirmed on Ubuntu 26.04 and Debian 13.
- **A compromised engine can make it build any repository.** The engine has no Docker socket, but this shortens its path to root: with a kernel or runc flaw, the build reaches root. It is an accepted risk, in the same family as write access to a deployed branch: see the [threat model](/docs/how-it-works/threat-model). A disposable builder under gVisor will close it: see the [roadmap](/docs/how-it-works/roadmap).
- **BuildKit image v0.25.2 or later.** It ships its own runc, which must be patched separately from Docker's.
- **Railpack and its BuildKit frontend are pinned by digest.**

<Callout type="warn" title="A malicious dependency can try to reach root">
  Because the builder's sandbox is weakened, a malicious dependency would have the means to attempt an escape to root, for example with the November 2025 runc vulnerabilities, which can be triggered from a Dockerfile. This is the cost of trusting the owner's code, dependencies included.
</Callout>

### User namespaces: not validated yet

The builder has to work with `userns-remap`, which Docker uses on the host, and this still needs early validation. rootlesskit maps the range `100000:65536` inside the container, beyond the 65,536 UIDs that `userns-remap` gives by default. A wider `dockremap` range will probably be needed.

### Network, resources and cache

- **Its own network, with internet access** (npm, pip), but blocked from the tailnet, private ranges, metadata endpoints and environment networks.
- **CPU and RAM limits, one build at a time.** A Next.js build can take all the RAM, and the OOM killer would then kill the apps or Brume.
- **Brume and Traefik get priority protection from the OOM killer.**
- **A separate cache per environment.** Otherwise a compromised build could poison the cache of the others, and a staging build the production one. See the [data model](/docs/how-it-works/data-model).

## Secrets during the build

- **Passed with `--secret`,** never with `ARG` or `ENV`: those stay in the image layers.
- **Masked in build logs.**
- **Build variables of static sites are public.** See [Runtime](/docs/how-it-works/runtime).

## Deployment and rollback

- **The builder never touches the runtime.** It produces an image. The agent loads it into dockerd and deploys it by digest.
- **The engine drives each deployment through a series of desired states.** Each step is an event in the log, so a deployment survives a crash of the engine, and the agent does not have to remember a deployment in progress.
- **No downtime for a service without a volume.** The new container starts next to the old one. Once its healthcheck passes, the Traefik route and the environment's DNS alias switch to it, then the old one stops. If the healthcheck fails, the new container stops and the old one keeps running.
- **A service with a volume stops, then restarts.** Two containers never share a volume, so the downtime lasts as long as the startup, and the panel shows it.
- **A static site switches instantly.** See [Runtime](/docs/how-it-works/runtime).
- **A deployment is marked successful on what the agent observed:** the container started and its healthcheck passed.
- **Rollback redeploys the digest of a previous revision,** without a rebuild. The [data model](/docs/how-it-works/data-model) lists what comes back with it and what does not.
