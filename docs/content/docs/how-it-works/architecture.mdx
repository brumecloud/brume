Brume is a single signed binary, `brume`, started as several systemd services. Each service has its own system user, its own permissions and its own hardening. Installing Brume stays simple, but a flaw in one service does not give the rights of the others.

## Overview

```text
Internet ─► Cloudflare ─► cloudflared ─► Traefik ─┬─► apps, Caddy
                                                  └─► brume webhook ──┐
                                                                      │ webhook.sock
Tailnet ──► tailscale serve ──► brume api ────────────────────────────┤ api.sock
                                                                      ▼
                      GitHub, notifications ◄─────────────────── brume engine ──► S3: log, blobs, keys
                                                                   ▲      │
                                             observations, facts   │      │   desired state, jobs
                                                                   │      ▼   (agent.sock)
                      S3: backups, artifacts ◄────────────────── brume agent ──► dockerd ──► containers
                                                                                   │
                                                       brume telemetry ◄───────────┘ app logs
```

Public traffic enters through Cloudflare and Traefik, which route it to the apps, to Caddy and to the webhook. Administration enters through the tailnet and `tailscale serve`, which lead to `brume api`. The webhook and the API reach `brume engine` only through their unix sockets.

The engine decides, and `brume agent` acts: the engine sends the agent the desired state of its machine, and the agent, which alone holds the Docker socket, makes it exist. The engine ships the state to S3, the agent ships the backups and the build artifacts. Every service also sends its own telemetry to `brume telemetry`: see [Observability](/docs/how-it-works/observability).

The diagram shows the recommended modes: Cloudflare Tunnel for public traffic, Tailscale for administration. The other modes are chosen on the host: see [Networking](/docs/how-it-works/networking#other-modes) and [Admin panel](/docs/how-it-works/admin-panel).

## Components

| Component | Role | What it holds | If it is compromised |
|---|---|---|---|
| `brume engine` | The only owner of the state. Decides every command, checks sessions, decrypts secrets, ships the state to S3, checks for updates. | The master key, the state (SQLite), the GitHub App's private key, the S3 credentials (read and write, never delete), a read-only Cloudflare token. | The apps, their secrets and their data, within the limits of `policy.toml`. Not root on the host without a kernel or runc flaw. |
| `brume agent` | Drives Docker on its machine: applies the desired state and the policy, runs the builds and the backups. | The Docker socket, the same S3 credentials as the engine. | Everything, on its machine. With the updater, it is the only Brume component in this position, hence its minimal code. |
| `brume api` | Serves the panel and its API. | A socket to the engine. | Nothing without a session opened by the admin: the engine checks every session. During a session, the panel's actions, without the dangerous options. |
| `brume webhook` | Receives GitHub webhooks. | The HMAC secret, a socket to the engine. | Queuing a build of an already configured repository. |
| `brume telemetry` | Receives the apps' logs and Brume's own telemetry, stores them and queries them with DuckDB. | The logs, the telemetry. | Reading the logs and the telemetry. No network, no secrets, no Docker. |
| `brume updater` | Installs Brume updates. | The right to write the binaries. | Equivalent to root, but it runs only during an update and accepts only signed binaries. |
| Rootless BuildKit | Builds the images. | Outbound internet access, the GitHub token and the build secrets. | The current build, its secrets, the GitHub token and the cache of its environment. Its sandbox is weakened because it only runs trusted code: see [Builds and deployments](/docs/how-it-works/builds-and-deployments). |
| cloudflared | The tunnel connector. | The tunnel secret. | Reading and modifying public traffic. It reaches only Traefik and the webhook. |
| Traefik | HTTP routing. | Its config, read-only. | Reading and modifying public traffic, reaching the exposed services. Not the databases. |
| Caddy | Serves static sites. | The files, read-only. | Serving modified content until it restarts. |
| An app | The user's code. | Its environment network, its secrets. | Its environment, nothing else. |

## The engine

The engine is the control plane. It holds the state and the secrets, but not the Docker socket.

- **The only owner of the state.** No other service accesses it: the API, the webhook and the agent go through the engine. The state is an event log in SQLite, which the engine ships to S3 in the background.
- **It describes the desired state, the agent makes it exist.** The engine sends the agent the desired state of its machine, and records the facts the agent reports.
- **It checks every request against `/etc/brume/policy.toml`,** to show a clear error in the panel. The agent is the one that enforces the policy.
- **No untrusted data.** Each parser in the engine would be a door to the state and the secrets. So it does no git clone, no archive extraction, and no webhook or log parsing. It receives only typed values that are already validated.
- **No inbound network.** It listens only on unix sockets.
- **The owner of the sessions.** The engine checks the second factor, issues the session and validates it on every request from the API. A compromised API can do nothing without a session opened by the admin. See [Admin panel](/docs/how-it-works/admin-panel).
- **No Docker socket:** that is the agent's job. A compromised engine gives the apps, their secrets and their data, within the limits the agent enforces. It does not give root on the host without a kernel or runc flaw.
- **One path is shorter.** A compromised engine can have the builder build any repository, and the builder runs with a weakened sandbox: with a kernel or runc flaw, that leads to root. This is an [accepted risk](/docs/how-it-works/threat-model#accepted-risks-in-alpha-01).

## The agent

The agent is the only part of Brume that drives Docker. There is one per machine, and alpha 0.1 has one machine.

- **The only component that holds the Docker socket.** With the updater, it is the only Brume component equivalent to root, so its code stays minimal.
- **A reconciliation loop,** as in Kubernetes. The desired state received from the engine describes what must run, and the agent brings Docker to that state. After a crash or a reboot, it puts everything back in place on its own.
- **Drift detection.** A container, network or published port that Brume did not create, such as a `docker run -p` started by hand, is reported to the engine, which alerts.
- **Its own policy.** It builds each container's config from an allowlist and enforces `/etc/brume/policy.toml`, without trusting the engine. See [Runtime](/docs/how-it-works/runtime).
- **No untrusted data,** like the engine. The git clone and the extraction of static sites run in unprivileged processes.
- **It listens on nothing.** The agent connects to the engine, not the other way around.
- **If the engine stops,** the agent keeps applying the last desired state it received, restarts included, and changes nothing else. At boot, in 0.1, it waits for the engine before starting the containers. Starting without the engine is on the [roadmap](/docs/how-it-works/roadmap).

## How the services talk to each other

- **One unix socket per client.** `/run/brume/api.sock` belongs to the `brume-api` group, `/run/brume/webhook.sock` to the `brume-webhook` group, `/run/brume/agent.sock` to the `brume-agent` group. File system permissions do the authorization. The engine also listens on `admin.sock`, for the emergency CLI, root only.
- **Each socket has its own operations.** The webhook socket exposes only `enqueue_build(repo_id, ref)`.
- **A typed, versioned protocol,** with bounded message sizes. There is no generic operation such as "run a Docker command".
- **The engine sends the agent the full desired state of its machine,** never a diff, and one-off jobs such as a build or a backup. The agent sends back what it observes, and the facts that the engine records as events.
- **The engine does not take the agent at its word.** It checks that the agent only talks about the resources of its own machine. The machine is identified by the connection (`SO_PEERCRED`), never by the message.
- **Log collection does not go through the engine.** dockerd sends each container's logs directly to `brume telemetry`, so a flood of logs cannot saturate the engine. See [Observability](/docs/how-it-works/observability).
- **Log reading goes through the engine.** The API asks the engine for logs. The engine checks the session, then relays the answer from `brume telemetry` without interpreting it. The API streams the logs to the panel over SSE. `brume telemetry` never has access to Docker.
- **The builder never touches the runtime.** It produces an image, and the agent loads it into dockerd and deploys it by digest.

## Why the webhook is separate from the API

- **In the recommended mode, it is the only Brume component reachable from the internet.** Inside the API, a flaw in its parsing would give access to every admin action.
- **It does not listen in the same place.** The webhook is reachable from the ingress network, the API only through `tailscale serve` or an SSH tunnel. Merging them would force the API to listen on the internet side. With public administration, the API also listens on the ingress network, but it stays a separate process.
- **On its own, it stays tiny:** a few hundred lines and a single operation.

## Two-stage ingress

- **cloudflared is on the `tunnel` network,** to reach Cloudflare, **and on the `ingress` network,** with Traefik. Once compromised, it reaches only Traefik and the webhook.
- **Traefik is on `ingress`,** and on one `edge-<service>` network per exposed service. It is never on the environment networks, so it does not reach the databases.
- **Traefik listens only on its fixed IP on the `ingress` network.** On the edge networks, it only opens connections to the apps. An app therefore cannot call Traefik to reach another app without going through Cloudflare.
- **Traefik never has the Docker socket.** The agent writes its config (file provider) to a folder that Traefik mounts read-only.
- **Mounting the Docker socket with `:ro` protects nothing.** A read-only socket still accepts every Docker API call.
- **With direct ingress,** there is no cloudflared: Traefik publishes ports 80 and 443. See [Networking](/docs/how-it-works/networking#other-modes).

## Service hardening

Every service has a dedicated user, `NoNewPrivileges=yes`, `ProtectSystem=strict`, `ProtectHome=yes`, `PrivateTmp=yes`, and `ReadWritePaths=` limited to its own folder in `/var/lib/brume`.

| Service | Allowed network |
|---|---|
| `brume engine` | Unix sockets, and outbound to S3, GitHub, the Cloudflare API (read-only), brume.dev and the notification channels. |
| `brume agent` | Unix sockets (engine, Docker, tailscaled), and outbound to S3. |
| `brume api` | Localhost only (`IPAddressDeny=any`, `IPAddressAllow=localhost`), or the ingress network with public administration. |
| `brume webhook` | The ingress network only. |
| `brume telemetry` | None (`PrivateNetwork=yes`). |

`brume telemetry` also has memory and CPU caps (`MemoryMax=`, `CPUQuota=`), so a flood of logs cannot starve the server.

Without outbound network, code running in the API or the webhook can neither download tools nor send data out directly. Even a successful DuckDB injection in `brume telemetry` gets no network, no secrets and no Docker.

The agent's hardening matters little: with the Docker socket, it can do anything. It still gets it, against mistakes.

## Binaries and updates

- **The binaries belong to root,** and `ProtectSystem=strict` prevents the services from modifying them.
- **Brume updates itself.** The engine reads `https://brume.dev/latest.json`, a signed manifest of the latest release. It checks the signature before parsing the file, then starts the updater. See [Host and installation](/docs/how-it-works/host-and-installation).
- **A dedicated updater** redoes every check without trusting the engine: the [minisign](https://jedisct1.github.io/minisign/) signature, the version and the hash of the binary. It checks the signature against one of the two public keys built into the binary already installed: the signing key, and a backup key kept offline elsewhere. It then replaces the binary and restarts the services.
- **As a result,** a compromised service, other than the agent, cannot persist by replacing its own binary.
- **To decide before the first release:** the time of day updates are installed, a local rollback to the previous binary when a new one fails to start, and a staged rollout through a percentage in `latest.json`. See the [open decisions](/docs/how-it-works/roadmap#open-decisions). The update check sends no installation identifier: see [Host and installation](/docs/how-it-works/host-and-installation#telemetry-and-the-update-check).
