The admin panel is a React single-page app. CI compiles it and embeds it in the signed binary, so the server never runs npm (see [Development rules](/docs/customize/development#frontend)). `brume api` serves it with the API, on the same origin.

This page sets the stack, code layout, rules and tooling of the panel. The security rules of [Admin panel](/docs/how-it-works/admin-panel) and [Development rules](/docs/customize/development) take precedence over it.

## Stack

| Role | Choice |
|---|---|
| UI | React 19, with the React Compiler |
| Toolchain | Vite+ (`vp`): build, tests (Vitest), lint (oxlint), formatting |
| Types | Official TypeScript (`tsc`), in strict mode |
| Routing | TanStack Router, file-based routes |
| Server data | TanStack DB (collections synced by TanStack Query), TanStack Query alone for what is not an entity |
| Components | [coss ui](https://coss.com/ui) on Base UI, Tailwind v4, `cva`, `tailwind-merge`, lucide icons |
| Canvas | React Flow (`@xyflow/react`) |
| Animations | `motion` |
| Mock data | MSW, in `mock` mode, in tests and in the brume.dev demo. Normal development talks to the real API. |
| Browser tests | Vitest in browser mode, headless Chromium through Playwright, `vitest-browser-react` |

**No global store** (zustand, Redux) in 0.1. Shared state comes from the TanStack DB collections, which are only a cache of the server state, or from the URL. Everything else is local state.

## Code layout

The code has three layers, from top to bottom. A layer imports only the layers below it.

```text
web/
├── src/
│   ├── routes/                1. routing and pages: parameters, loader, component assembly
│   ├── components/ui/         2. coss primitives
│   ├── components/<domain>/   2. components: local state, data, rendering
│   ├── hooks/                 2. shared hooks
│   ├── helpers/               3. pure functions, tested in Node: all the logic
│   ├── api/                   the only code that talks to the server: client, collections, queries, generated types
│   ├── mocks/                 the mock API (mock mode, tests and demo only)
│   └── lib/                   cn, used by components/ui
├── build/                     build plugins and their tests
└── oxlint-plugin/             Brume's own lint rules
```

- **A route assembles the page:** `createFileRoute`, the parameter validation, the `loader`, and a page component that places components. No state and no logic: the lint forbids `useState`, `useEffect` and `useRef` there.
- **A component owns its state and its data** (`useState`, `useLiveSuspenseQuery`, mutations), then reads, renders and delegates. It computes nothing: a sort, a filter or a format goes in `helpers/`.
- **A helper is a pure function,** with no React, no TanStack, no `api/` (except its types) and no component. The lint enforces it.
- **`*.test.ts` runs in Node, `*.browser.test.tsx` in Chromium.**
- **The `~/` alias** points to `src/`.
- **Same comment rule as for Rust:** comments are in English, and none repeats the code.
- **The interface is in English,** with dates and numbers in the `en-US` format.

`allowImportingTsExtensions` is there for `build/` and `oxlint-plugin/`, which Node runs directly: their imports keep the `.ts` extension. Imports in `src/` have no extension.

- **No `any`.** Unknown data is `unknown`, then validated.
- **Branded IDs** (`ServiceId`, `ProjectId`), the equivalent of Rust newtypes: you cannot pass one for the other. They live in `src/api/ids.ts`.
- **The API types are generated from Rust** with `ts-rs`, into `src/api/generated.ts`, which imports the IDs from `./ids`. `cargo test -p brume-api export_typescript_bindings` rewrites the file. With `BRUME_CHECK_BINDINGS=1`, the test fails instead if the file differs. Never edit the file by hand. `src/api/types.ts` re-exports it and keeps by hand only the types with no Rust equivalent. A shape mismatch is fixed on the Rust side, in the DTOs of `brume-proto`.
- **No `enum` and no `namespace`** (`erasableSyntaxOnly`): use string unions.
- **Inferred types** rather than annotated ones, except at boundaries (props, the API client).

## React

### The React Compiler memoizes for you

- **It is enabled on all of `src/`.**
- **No `useMemo`, no `useCallback`, no `"use memo"` or `"use no memo"` directive** (`brume/no-manual-memo`).
- **The compiler silently skips** any function it cannot prove correct, such as one that reads a ref during render or calls `setState` in an effect. The `react/*` lint rules turn these cases into errors.
- **The lint does not catch everything** (`try` with `finally`, `throw` inside a `try`). So a test, `build/react-compiler.test.ts`, compiles every file of `src/` and fails on any skip. The build keeps `panicThreshold: "none"`, as the React docs recommend.
- **One explicit exception:** a component that calls a library the compiler cannot memoize without freezing the display. The compiler reports it (`IncompatibleLibrary`) and leaves it uncompiled, which is correct. Today only `components/logs/log-list.tsx` is in this case, with `useVirtualizer` from TanStack Virtual. It is listed in `build/react-compiler.test.ts`, which fails for any other skipped file. The component only holds the glue with the library: the rows are compiled components.
- **The official Babel plugin,** wired through `@rolldown/plugin-babel` and `reactCompilerPreset()` from `@vitejs/plugin-react`. **Babel 7, not Babel 8:** `babel-plugin-react-compiler` 1.0 does not read the Babel 8 AST and skips every function that has a default value in its props. The test above caught it.

### Every effect says why it exists

`brume/no-unreasoned-effect` flags every `useEffect`, `useLayoutEffect` and `useInsertionEffect`. Before you keep one, check whether something else does the job:

| If the effect… | Do this instead |
|---|---|
| Computes something from props or state | Compute it during render. |
| Responds to an action | Do it in the event handler. |
| Resets state when a prop changes | Put a `key` on the component. |
| Loads data | Use TanStack Query. |
| Reads a value from outside React | Use `useSyncExternalStore`. |

An effect only belongs when it syncs the component with something outside React: a DOM node, a listener, a timer, an SSE connection. It then states its reason:

```tsx
// oxlint-disable-next-line brume/no-unreasoned-effect -- opens the log SSE stream and closes it on unmount
useEffect(() => subscribeToLogs(serviceId, append), [serviceId]);
```

**Every lint or type suppression says why** (`brume/require-suppression-reason`). A suppression that is no longer needed is an error.

## Components and styles

- **The exports of `components/ui` own their look.** You pick a `variant` or a `size`; you do not restyle them with `className`. Layout classes (width, flex, margin, position) go on the parent.
- **When a look is missing:** if it is generic, it becomes a new variant of the component. If it is specific to one feature, it stays in that feature's component.
- **No borrowed class recipes:** `buttonVariants` and the like are not imported outside `components/ui`. Render the component instead (`render={<Button />}`).
- **No raw `<button>`, `<input>` or `<select>` styled** to look like a control that a primitive already provides.
- **Composition through slots:** a component exports small subcomponents, named the way coss names its own (`Banner`, `BannerTitle`, `BannerActions`). Each one carries its own classes, accepts `className` and merges it with `cn`. Compose or extend them, do not copy the markup. Examples: `components/common/callout.tsx` (`Callout`, `CalloutIcon`), the notice in the variable and rollback dialogs, and `components/variables/variable-item.tsx` (`VariableItem`, `VariableItemName`, `VariableItemValue`, `VariableKindBadge`…), the variable row shared by a service's tab and the shared variables.
- **Tailwind goes in the component that renders the element.** Global CSS is only for what classes cannot express: theme variables, animations. No `style={{…}}` for a static value. The theme goes through `@variant dark`.
- **Two registries only: coss ui (`@coss`) and the official shadcn registry.** coss is maintained by Cal.com, on Base UI and Tailwind v4 like the rest of the stack. The shadcn CLI copies the source code into the repository, so review that code as you would Brume's own. Add only the components you use (`pnpm dlx shadcn@<version> add @coss/<component>`), never all of `@coss/ui`.
- **shadcn's Chart is not added as is:** its `ChartStyle` injects a `<style>` through `dangerouslySetInnerHTML`. It is removed, and the series colors go through the theme's `--chart-*` variables. The chart library itself is still an [open decision](/docs/customize/frontend#open-decisions).
- **Mobile friendly:** touch targets are at least 44 px on coarse pointers (`pointer-coarse:`).
- **A pending state shows as a blue outline** (`outline-info`), set by `data-staged` or `data-draft`: on a setting, a variable row, a canvas card.
- **Logs have a terminal background** (`bg-terminal`), darker than the cards.
- **A long list is searchable:** `SearchSelect` (the coss combobox, with a search field in the list) for projects, environments, repositories and branches. Its trigger has an `aria-label`, because a combobox does not take its name from its content.
- **A `Select` opens below its trigger,** never over it (`alignItemWithTrigger` is `false` by default in `ui/select.tsx`).

## Routes

- **File-based routes, with `autoCodeSplitting: true`.** `routeTree.gen.ts` is generated, and excluded from lint and formatting.
- **A route file is thin:** `createFileRoute`, the parameter validation, the `loader`, and a page component that assembles components from `components/`.
- **A project's rail** leads to the canvas, the logs, the shared variables (`$env/variables`) and the activity (`$env/activity`). `hooks/use-project-page.ts` (`PROJECT_PAGES`, `useProjectPage`) tells which page is open. The rail uses it for its active state, and the environment switcher uses it to stay on the same page in the other environment. From a service panel, the switcher opens the other environment's canvas, because a service belongs to one environment only.
- **`/login` reads the login link's token** (`#token=…`, `helpers/session.ts::parseLoginHash`) in the route's `loader`, not in an effect: a one-time token must not be spent twice by StrictMode's double effects. With a session open, it goes to `/projects`. Otherwise the page says to run `brume dev` and open the link it prints, or that the link has expired.
- **URL parameters are hostile input:** anyone can send a crafted link to the admin. `validateSearch` accepts only known values and caps the length of strings. Path parameters (`$serviceId`) go through `params.parse`. The parsing is a tested helper, and an invalid parameter gives a `notFound()`.

```tsx title="web/src/routes/projects/$projectId/$env/logs.tsx"
import { createFileRoute, getRouteApi } from "@tanstack/react-router";

import { LogExplorer } from "~/components/logs/log-explorer";
import { parseLogsSearch } from "~/helpers/logs";

const projectRoute = getRouteApi("/projects/$projectId/$env");

export const Route = createFileRoute("/projects/$projectId/$env/logs")({
  validateSearch: parseLogsSearch,
  component: LogsPage,
});

function LogsPage() {
  const { environment } = projectRoute.useLoaderData();
  const search = Route.useSearch();
  return <LogExplorer environmentId={environment.id} search={search} />;
}
```

## Data

- **One HTTP client, in `src/api/`.** It calls relative URLs (`/api/…`), adds `X-Brume: 1` and `Content-Type: application/json`, and turns errors into a known type. `fetch` and `EventSource` are forbidden everywhere else.
- **An expired session goes back to `/login`.** A 401 outside the `/api/session` routes sends the tab to `/login` with `window.location.assign`, once (a module flag): every query fails at the same time, and the reload also clears the caches.
- **Every response is decoded** by a helper (`helpers/decode.ts`) before it gets a type: its shape is checked, not assumed.
- **One TanStack DB collection per entity of the model** (projects, environments, services, deployments, variables), built with `queryCollectionOptions`. The route `loader` calls `collection.preload()`. Components read with `useLiveSuspenseQuery({ query })`, through named queries in `api/` (`projectById(id)`, `projectEnvironments(id)`). Mutations are optimistic, except those that carry the value of a secret.
- **Nothing pushes status changes to the panel.** The services and deployments collections refetch every 2 seconds (`refetchInterval`, `IN_FLIGHT_POLL_MS`) while one of their rows is `building` or `deploying`, and stop once none is.
- **TanStack Query alone** for what is not an entity: metric series, database statistics, build logs, the activity pages (`infiniteQueryOptions`, pages of 100 events from the newest back, shown in log order).
- **TanStack DB is still at 0.x.** Version 1.0 will come through a normal update, once the [`minimumReleaseAge`](/docs/customize/frontend#dependencies) delay has passed.
- **Revealing a secret is a mutation:** it is a `POST`, and it is logged. It runs with `gcTime: 0`, and the value never enters the query cache.
- **Live logs arrive over SSE,** as [Admin panel](/docs/how-it-works/admin-panel) specifies. The tab keeps the last 50,000 lines. A reconnected stream sends its history again, and the lines already received are skipped.
- **The log list is virtualized (TanStack Virtual):** only the visible lines are in the DOM, each one measured, since a line can wrap. See the [React Compiler exception](/docs/customize/frontend#the-react-compiler-memoizes-for-you).
- **`EventSource` cannot send `X-Brume`.** The log stream is a `GET` without side effects: the server protects it with Fetch Metadata (`Sec-Fetch-Site: same-origin`), and no CORS makes it readable from another site. See [CSRF and cross-site requests](/docs/how-it-works/admin-panel#csrf-and-cross-site-requests).
- **A log line opens on click** and shows the whole line as indented JSON (`logJson`). A message that is itself JSON appears there as `data`, not as an escaped string. Highlighting goes through `jsonTokens`, rendered as text `<span>` elements. Opening a line stops following the stream.
- **The histogram stacks the levels** in each bar (info, warning, error), in the colors of the log lines.
- **ANSI colors:** a parser written for Brume (`helpers/ansi.ts`) splits each line into `{ text, style }` segments, rendered as `<span>` elements with classes. It keeps only color codes, and strips every other sequence (cursor, window titles, OSC links) and control characters. Never HTML, and never a library that produces HTML: log lines can come from an attacker (see [XSS](/docs/how-it-works/admin-panel#xss)).
- **URLs that come from the API** (an app's domain, a commit link) are shown as links only if their scheme is `https:`.

### Pending changes

A changed setting or variable does not apply right away: it waits for the next deployment of the environment, as on Railway.

- **The draft lives on the server** (`/api/changes`), not in the browser. It survives a reload, and the value of a pending secret never comes back from it (`null`). So `changesCollection` holds no secret.
- **One change per setting or variable:** staging a new one replaces the old one. Going back to the applied value removes the change (`settingChange`).
- **Staging is not optimistic** (`stageChange` sends the change, then reloads the collection), for the same reason as creating a secret. Discarding a change is optimistic.
- **A bar floats at the top of the canvas,** centered on the space the service panel leaves free (`--spacing-panel`), and counts the changes of the environment. "Détails" lists them by service. "Déployer" (or ⇧ Enter) applies them all, with one new revision per service touched. The ⋮ menu discards them all.
- **The tabs show the state after the next deployment:** `withStagedSettings` and `stagedVariableRows` lay the changes over the applied values.
- **Referencing a shared secret** from a service's Variables tab ("Shared secret") stages a secret variable with no value (`value: null`), resolved at deploy time on the service, then the environment, then the project. While staged, it looks like a secret of the service itself. Once deployed, the row carries a "Shared" badge and cannot be revealed or edited.

### Shared variables and activity

- **The Variables page** (`$env/variables`) lists the project's variables and the environment's. Editing or deleting a plain or build variable first lists the services it reaches, environment by environment, production first (`GET /api/variables/impact`, `hooks/use-variable-impact.ts`). Confirming redeploys them. A shared secret is saved at once, then the panel offers to redeploy the services that reference it. Deleting a secret that is still referenced shows the server's refusal.
- **The Activity page** (`$env/activity`) lists the project's events in log order, opens on the newest one, and loads older ones above. Each event's summary is rendered as text.

### Real API and mock API

- **`pnpm dev` talks to the real API.** In `development` mode, a plugin in `vite.config.ts` (`brume:real-api`) proxies `/api` to `http://127.0.0.1:7878`, the API of `brume dev`, on the same origin. The dev server listens on port 5173 with `strictPort`: the API's `Host` allowlist knows 5173 and no other dev port, so Vite fails to start rather than move to a port the API would refuse. The proxy keeps the browser's `Host`. See [Run Brume locally](/docs/customize/run-locally).
- **`pnpm dev:mock`** (`vp dev --mode mock`) keeps the mock API, with no proxy. The tests (`test` mode) and the demo never leave MSW.

MSW mocks the API in the browser:

- **`src/mocks/`:** a dataset (`seed.ts`) and handlers that answer like the API, with latency. They reject a request without `X-Brume`, like the real server. An `/api` route with no mock answers 501.
- **An admin is always signed in:** the mock and the demo open without a login link.
- **Out of the build:** `main.tsx` starts MSW only in `mock` mode or in the demo. The production build contains neither the worker nor the handlers.
- **Browser tests use the same handlers.**
- **The generated types are the API contract** (`src/api/generated.ts`). The handlers and the decoders follow them: a shape mismatch is fixed on the Rust side, so the mocks and the panel tests stay valid.

## Canvas

- **React Flow runs in uncontrolled mode:** it keeps the node state (positions, measurements, selection). The graph is rebuilt (`key`) only when its shape changes: a service or a dependency added or removed.
- **Each node reads its service by id** from the TanStack DB collection. A status change redraws the card without rebuilding the graph.
- **Automatic layout** (`helpers/canvas.ts`): a service sits one row above the services it depends on. Apps are at the top, their databases below.
- **Positions moved by hand** stay in the browser, in a TanStack DB collection on localStorage. They are display preferences, not project data. "Réorganiser" (rearrange) clears them.
- **Edges come from the dependencies,** which the API computes from the secrets each service references.
- **The React Flow attribution stays visible:** its license requires a Pro subscription to hide it.
- **A service's panel is a child route of the canvas** (`$env/_canvas/services/$serviceId/{deployments,variables,settings}`). The canvas stays mounted behind it, the Back button closes the panel, and each tab has its own URL. The canvas shifts to keep the selected service visible left of the panel (`panelFocusCenter`).
- **A deployment takes the place of the service panel** (`deployments/$deploymentId`), and the service panel steps back to the bottom left: its edge stays visible underneath, like a card under another one. The deployment renders through a portal into the canvas layer (`PanelLayer`, `StackedPanel`), because inside the service panel it would be clipped by it and placed against it.
- **The panel steps back with a CSS `transform` on a wrapper,** which motion ignores. For motion, the deployment is still a child of the panel, since motion follows the React tree, not the DOM. As a motion value, the step back would offset the deployment's layout animations: the underline of its tabs jumped.
- **The deployment slides in without a fade:** a fade would show the panel header through its own. Its tabs (details, build logs, runtime logs) go through the `tab` URL parameter.
- **The settings scroll on their own,** so their navigation follows the section being read (`currentSection`). A click in the navigation pins its section until the next manual scroll: otherwise, at the bottom of the page, the last section would take its place.
- **A canvas card shows its pending changes** with a blue outline and their count.
- **React Flow pulls in `zustand`** for its internal state. The "no global store" rule covers Brume's code, not the code of its dependencies.

## Animations

- **`motion`,** with the rules of the `improve-animations` skill (`.claude/skills/improve-animations/AUDIT.md`).
- **One reason per animation.** Nothing on what you use a hundred times a day: the command palette, shortcuts.
- **Under 300 ms,** with `ease-out` on entry. Curves and durations are theme variables, never typed in a component.
- **`transform` and `opacity` only.** Popovers grow from their trigger (the `--transform-origin` of Base UI).
- **`prefers-reduced-motion`:** opacity stays, movement goes. `MotionConfig reducedMotion="user"` at the root does it for moves (`x`, `y`) and layout animations.
- **Vercel-style tabs** (`NavTabs`): a single pill per bar slides to the hovered tab (`x` and `width`, computed by `helpers/tabs.ts`). It fades only when the pointer enters or leaves the bar. One pill per tab linked by `layoutId` flickered, one fading out while the other faded in. The underline slides to the active tab (`layoutId`). Each tab bar has its own `LayoutGroup`, because two bars can be on screen at the same time.

## Security enforced by tooling

| Rule | How |
|---|---|
| Never `dangerouslySetInnerHTML` | `react/no-danger` set to error |
| CSP without inline scripts | No inline `<script>` in `index.html`. The theme applied before the first render loads from a file, under `'self'`. |
| Trusted Types | Brume's code never inserts raw HTML. A dependency that does is refused. |
| No `eval` | `eslint/no-eval`, `eslint/no-new-func`, `eslint/no-script-url` |
| `X-Brume` header on every request | `fetch` and `EventSource` forbidden outside `src/api/`. Only the log SSE stream goes without it, see [Data](/docs/customize/frontend#data). |
| External links | `react/jsx-no-target-blank` |

In development, Vite injects inline scripts (HMR, React Refresh). The strict CSP applies to the build that `brume api` serves.

**Only three custom rules:** `no-manual-memo`, `no-unreasoned-effect` and `require-suppression-reason`. They are short, written for Brume, live in `web/oxlint-plugin/`, and are tested with the oxlint `RuleTester`.

### Review: two audit skills

`.claude/skills/improve-react` and `.claude/skills/improve-animations` audit the code at the end of each batch of work and propose plans. They do not change anything themselves.

- **This page takes precedence.** improve-react relies on the React Doctor rules. Those that push for manual memoization (`jsx-no-new-function-as-prop`, `jsx-no-new-object-as-prop`, `rerender-dependencies`, `no-inline-prop-on-memo-component`) do not apply: the React Compiler handles it.
- **React Doctor is not installed.** It pulls in `@sentry/node`, a TypeScript older than 6 and its own oxlint. The audit uses the rule catalog of the skill (`AUDIT.md`), without the scanner.

## Tests

- **Two Vitest projects:** `unit` in Node (`src/**/*.test.ts`) and `browser` in headless Chromium (`src/**/*.browser.test.tsx`). No jsdom and no happy-dom: a real browser.
- **Test logic and observable behavior.** No markup snapshots, and no test that only checks that a callback is wired.
- **For a logic or data bug,** write a failing test first, then the fix. For a purely visual bug, take a before and after screenshot instead of writing a test.
- **Never wait for real:** no `sleep`, no polling loop, no duration measurement. Use fake timers, and assert with `expect.element` or `vi.waitFor`.
- **`retry: 0`:** a flaky test gets fixed, not rerun.
- **`allowOnly: !process.env.CI`:** a forgotten `.only` fails CI.
- **`vitest-browser-react` unmounts components** before each test, even after a failure. Its `render` is not disposable (`await using`) yet.
- **Browser tests go through the MSW handlers,** like `mock` mode does. A test mounts the whole app on a URL (`test/render-app.tsx`) and checks what the admin sees. Test files run one after the other: they share the MSW service worker, and iframes running in parallel would mix their requests.
- **The mock API keeps its state between the tests of a file.** A test that stages a change deploys or discards it before it ends.
- **A test closes the dialogs it opened** (Escape) before it ends. A modal makes the rest of the page inert, and the cleanup between tests unmounts it too abruptly to undo that: the next test renders under it, on a blank page with nothing to click (see `test/render-app.tsx`). A `screen.unmount()` followed by a second render in the same test falls into the same trap.
- **Vite's pre-bundling crawls every file at startup** (`optimizeDeps.entries`). A dependency found mid-run reloads the tests and makes them fail.
- **`build/react-compiler.test.ts`** compiles every file of `src/` and fails if the compiler skips a function in it.

## Build

- **No cycle between chunks.** A Vite plugin of a few lines (`build/no-chunk-cycles.ts`) fails the build if two chunks import each other. A cycle can run a chunk before its dependencies and leave a blank page.
- **Reload after an update.** Every Brume update removes the old chunks from the binary. So a tab left open reloads the page once on `vite:preloadError`, with a `sessionStorage` flag to prevent reload loops.
- **Output goes to `web/dist`,** which CI embeds in the binary.

An excerpt of the pnpm workspace:

```yaml title="web/pnpm-workspace.yaml"
packages:
  - .

catalog:
  react: 19.3.1
  react-dom: 19.3.1
  "@tanstack/react-query": 5.104.5

overrides:
  vite: npm:@voidzero-dev/vite-plus-core@1.4.0
  vitest: 5.0.5

savePrefix: ""

minimumReleaseAgeExclude: []

  - semver@6.3.1

```

- **The pnpm workspace lives in `web/`,** not at the repository root: the root stays for the Rust code.
- **pnpm 12,** pinned by `packageManager`. Corepack cannot run it yet, so use `npx pnpm@<version>` in the meantime.
- **The catalog declares each version once, as an exact version.** `package.json` refers to it with `catalog:`.
- **`minimumReleaseAge: 10080`,** that is 7 days. The pnpm default is one day and not strict: when no version is old enough, pnpm installs a recent one anyway. An explicit value makes the check strict.
- **`minimumReleaseAgeExclude` stays empty.** An urgent security fix is added to it explicitly, then removed.
- **`trustPolicy: no-downgrade`:** the install fails if a version has less evidence of trust (trusted publisher, provenance) than the earlier ones. `trustPolicyExclude` lists the reviewed exceptions: `semver@6.3.1` was published before npm provenance existed, which is not a change of publisher.
- **Install scripts:** `strictDepBuilds` (true by default) fails the install if a package has a script nobody reviewed. `allowBuilds` lists the reviewed ones, set to `false` by default.
- **`blockExoticSubdeps` keeps its default** (true): no transitive dependency from git or from a tarball URL.
- **`overrides`** keep a single copy of each package.
- **`packageManager` is pinned** in `package.json`. `trustPolicy` checks that pnpm version too.
- **`knip`** reports unused dependencies and exports.
- **Every new runtime dependency is discussed in a PR:** what it brings, who maintains it, and what it pulls in with it.

## Open decisions

These two questions are not settled yet.

1. **Decoding API responses:** decoders written by hand (`helpers/decode.ts`, today), or a schema library (zod, valibot) whose schemas TanStack DB accepts. To be decided when the model grows.
2. **Metrics charts:** shadcn's Chart (Recharts, which pulls in Redux Toolkit, immer and d3), without its `ChartStyle`. To be confirmed with the metrics batch.

Settled:

- **The React Compiler** goes through the official Babel plugin (Babel 7).
- **TanStack DB** is adopted.
- **The types in `src/api/` are generated from the Rust types,** with `ts-rs` (see [TypeScript](/docs/customize/frontend#typescript)). Types written by hand would drift from the Rust ones. An OpenAPI schema comes later, when the API opens to other clients (API tokens, a remote CLI).
