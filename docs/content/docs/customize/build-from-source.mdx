Brume ships as one signed binary, `brume`, with the React panel compiled and embedded in it. To build it yourself, you build the panel first, then compile the Rust code, which embeds the panel. If you want your servers to accept your builds as updates, you also sign them with your own minisign key.

<Callout title="No code yet">
  Brume is in its design phase. This page describes the toolchains, checks and signing that the design fixes for alpha 0.1.
</Callout>

## Prerequisites

- **Stable Rust.** Brume builds on the stable toolchain, and the code uses no unstable feature.
- **Nightly Rust, for formatting only.** Three options in `rustfmt.toml` are unstable, so formatting runs with `cargo +nightly fmt`.
- **pnpm 12,** pinned by `packageManager` in `web/package.json`. pnpm's trust policy checks that version too. Corepack cannot run pnpm 12 yet: use `npx pnpm@<version>` until it can.
- **`cargo deny` and `cargo audit`,** to run the dependency checks of CI.
- **Chromium, through Playwright,** for the panel's browser tests.
- **minisign,** to sign your builds.

## Build the panel and the binary

<Steps>

<Step>

### Install the panel's dependencies

The pnpm workspace lives in `web/`, not at the repository root, which stays for the Rust code. In `web/`, run:

```bash
pnpm install --frozen-lockfile
```

The panel's code runs with the admin's rights: a compromised npm package gets every action of the panel. So `web/pnpm-workspace.yaml` makes the install strict:

- **A 7-day delay before a new version installs** (`minimumReleaseAge: 10080`). pnpm's default is one day and not strict: without a version old enough, it installs a recent one.
- **No drop in trust** (`trustPolicy: no-downgrade`). The install fails if a version has less evidence of trust, such as a trusted publisher or provenance, than the versions before it.
- **No unreviewed install script.** The install fails if a package has an install script nobody reviewed (`strictDepBuilds`).
- **No transitive dependency from git or a tarball URL** (`blockExoticSubdeps`).
- **Exact versions, declared once** in the workspace catalog.

</Step>

<Step>

### Build the panel

```bash
vp build
```

Vite+ writes the panel to `web/dist`. The build fails if two chunks import each other: a cycle can run a chunk before its dependencies and leave a blank page.

The server never runs npm. The panel reaches it only inside the signed binary.

The API's TypeScript types, in `src/api/`, are generated from the Rust types, with `ts-rs` or `specta`, whichever the implementation picks. See [Panel frontend](/docs/customize/frontend#open-decisions).

</Step>

<Step>

### Compile the binary

Compile the Rust code with the stable toolchain. The binary embeds the panel from `web/dist`, and `brume api` serves it with the API, on the same origin. Brume runs on amd64 and arm64, and each official release ships one binary per architecture.

This one binary runs every part of Brume, with one subcommand per service. `brume engine`, `brume agent`, `brume api`, `brume webhook` and `brume telemetry` each run as their own systemd service, with their own system user, so a flaw in one does not give the rights of the others. `brume updater` runs only during an update, started by the engine. See [Architecture](/docs/how-it-works/architecture).

</Step>

<Step>

### Sign your build

Brume signs its official releases with minisign. The private keys stay offline, and two public keys are embedded in the binary: the signing key, and a backup key kept offline in another place. If the signing key is lost or stolen, a release signed with the backup key replaces it. Because the keys are offline, a compromised GitHub account cannot sign an update. The binaries and `install.sh` are published on GitHub Releases, from an account protected by a physical 2FA key.

Each official release also has a signed manifest: the version of the manifest's format, the release's version, whether it compacts the event log, and the hash and GitHub Releases address of the binary. The manifest of the latest release is published as `latest.json` on brume.dev, with an expiry date, and is signed again regularly even without a release.

To sign your own builds, follow the same scheme:

- **Keep your private keys offline,** for the same reason.
- **Embed your public keys in the binary,** a signing key and a backup key, from your first build. The updater checks every update against the keys embedded in the binary already installed, so a key added later would not protect the servers still running earlier versions.
- **Sign a release manifest that carries the version.** Put the version in the signed content, never in minisign's untrusted comment, which is not authenticated.
- **Say in the manifest when a release compacts the log.** The updater installs such a release before any later one: an installation left on the old log generation could no longer read its log.

</Step>

</Steps>

## Check your build

Run the checks that CI runs. For the Rust code:

```bash
cargo +nightly fmt --check
cargo clippy -- -D warnings
```

CI also runs `cargo deny` and `cargo audit` on the dependencies, and `cargo deny` checks the crate graph too. On every PR, CI runs the deterministic simulation and the conformance tests. A failing simulation prints its seed, and `BRUME_SEED=0x… cargo test -p brume-sim` replays it exactly. See [Development rules](/docs/customize/development#tests).

For the panel, in `web/`, after `pnpm install --frozen-lockfile`:

```bash
vp fmt --check
vp lint
tsc --noEmit
vp test run
knip
vp build
```

- **`vp lint`** runs oxlint with Brume's security and React rules.
- **`tsc --noEmit`** checks types in strict mode.
- **`vp test run`** runs the unit tests in Node and the browser tests in headless Chromium.
- **`knip`** reports unused dependencies and exports.

If you run your own CI on GitHub Actions, pin each action by SHA: the tj-actions attack of 2025 went through a modified tag. A `systemd-analyze security --offline=true` check is planned for later. The full rules are in [Development rules](/docs/customize/development).

## What your own key changes

The updater accepts only binaries signed with one of the two keys embedded in the binary already installed. So the keys your build carries decide which updates a server accepts:

- **A build with your keys** accepts only binaries signed with your keys. Brume's official releases fail the check, so you sign every update yourself.
- **A build with Brume's keys** accepts Brume's official releases as updates.
- **No going back.** The updater refuses any version lower than or equal to the installed one, so each of your releases needs a higher version in its signed manifest. An old vulnerable version stays signed forever: without this check, an attacker could reinstall it.
- **The official `install.sh` installs Brume's releases.** It downloads Brume's binaries from GitHub Releases and checks their signature before running `brume install`.

By default, Brume updates itself: the engine reads `https://brume.dev/latest.json`, checks its signature before parsing it, and starts the updater when a newer version exists. The updater does not trust the engine and runs every check again. You can turn the check off on the host, as root: Brume updates then become manual. Some details of automatic updates are still open, such as the time of day they install and a local return to the previous binary if the new one fails to start. See [Host and installation](/docs/how-it-works/host-and-installation) and the [open decisions](/docs/how-it-works/roadmap#open-decisions).
