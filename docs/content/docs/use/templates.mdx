Brume offers four templates: static site, PostgreSQL, MongoDB and Redis. Each one applies good practices that the panel cannot turn off. You pick a size and a few typed settings; Brume writes the config.

## How templates work

- **A template is a typed recipe compiled into the signed binary.** There is no YAML file to edit. Each template has a version: a new version ships with a Brume release, and reconciliation applies it with a short restart of the service.
- **Settings are typed and bounded:** size, Redis mode, tailnet access, and the settings listed for each template below. Each setting has a name, a type and bounds. Brume translates it into the config it generates: no value is passed through as is.
- **No free-form flags, environment variables or config files.** A setting that weakens security is offered only if it is listed on this page, and it is off by default.
- **A database receives none of the shared variables or secrets** of the project or the environment. A static site receives the shared build variables: they feed its build, not the nginx container. See [Core concepts](/docs/use/concepts).
- **The config is generated by serialization** and mounted read-only in the container. See [Development](/docs/customize/development) for the rules on generated config.
- **A new database gets the latest major version only.** That version does not change afterwards: major upgrades are not in 0.1, see the [roadmap](/docs/how-it-works/roadmap). The panel flags a major version that reaches its end of support. Minor versions follow Brume releases.

## Static site

The nginx container, the extraction of build artifacts and rollback are described in [Runtime](/docs/how-it-works/runtime). The template adds:

- **Cache:** `Cache-Control: immutable` for one year on files whose name contains a content hash, and `no-cache` on HTML. A rollback stays instant, even through the Cloudflare cache.
- **Headers:** `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and `Content-Security-Policy: frame-ancestors 'self'` against clickjacking. HSTS comes from Cloudflare.
- **Requests:** `GET` and `HEAD` only, no directory listing, and no server version in responses.
- **Real 404s by default.** The SPA fallback to `index.html` is a setting.
- **`.map` files are not served by default:** they expose your source code.
- **Artifacts are limited in total size and file count,** checked during extraction, against archive bombs.
- **Settings:** SPA fallback, `.map` files, and a full Content-Security-Policy (the value is validated and cannot contain a line break).

## What every database gets

- **The official image, pinned by digest.**
- **Started directly as the database user,** without the image's root entrypoint. All capabilities are dropped, the file system is read-only, and sockets and `/tmp` live on tmpfs.
- **The environment network only.** Never the edge network, egress or a domain. Tailnet access is turned on one database at a time: see [Networking](/docs/how-it-works/networking).
- **Two credentials, generated by the engine:**
  - an admin account, kept by the engine for backups and maintenance, which you can reveal;
  - an account for your app, with the fewest rights it needs.

  A linked service receives `DATABASE_URL`, `MONGODB_URI` or `REDIS_URL` with the app account. An injection in your app gets the app's rights, not the database's. These URLs contain the password: they are secrets, resolved at deploy time and never copied into a revision.
- **A memory size picked from a fixed list.** The database cache is derived from it. Without it, the database sizes itself on the host's RAM, and the OOM killer kills it.
- **A clean shutdown:** the right stop signal, and 60 seconds before `SIGKILL`. By default, Docker kills the container after 10 seconds, and the database has to repair itself on the next start.
- **A healthcheck in the container.** A failing database triggers an alert.
- **Backups on by default,** with the restore test described in [Secrets and backups](/docs/how-it-works/secrets-and-backups). Without S3 configured, the panel shows a permanent warning.
- **Logs sent to `brume logs`,** and queries are never logged.
- **No TLS between your apps and the database:** the traffic stays on the host bridge, or inside WireGuard over the tailnet.

## PostgreSQL

- **`scram-sha-256` authentication only,** from the environment's subnet. `POSTGRES_HOST_AUTH_METHOD` is never set.
- **The app role owns its database,** but is not a superuser and cannot create roles or databases. So it cannot run `COPY … PROGRAM`, use an untrusted language, or run `ALTER SYSTEM`. It can create extensions marked `trusted`.
- **`allow_alter_system = off`:** even the superuser cannot change the config persistently through SQL.
- **`log_statement = none`:** otherwise an `ALTER ROLE … PASSWORD` would write the password to the logs.
- **`idle_in_transaction_session_timeout` is set:** a forgotten transaction does not hold its locks forever.
- **`shared_buffers` at 25% of the memory limit.**
- **Stopped with `SIGINT`,** the Postgres fast shutdown.
- **Backups:** `pg_dump` for each database, plus the roles (`pg_dumpall --globals-only`).
- **Settings:** `max_connections`, `work_mem`, `statement_timeout`, `idle_in_transaction_session_timeout`.

## MongoDB

- **Authentication on,** with SCRAM-SHA-256. The app user has the `readWrite` role on its own database only.
- **A single-node replica set:** transactions, change streams and Prisma need one. Brume initializes it on first start.
- **A replica set keyfile,** generated by the engine and written to the database volume with mode `0400`. MongoDB reads it only from a file: it is the one exception to secrets passed as environment variables.
- **From your laptop, connect with `directConnection=true`:** the replica set member's name exists only inside the environment network.
- **`security.javaScriptEnabled: false`:** no server-side JavaScript (`$where`, mapReduce). That is one NoSQL injection path fewer.
- **The WiredTiger cache is fixed** with MongoDB's formula, applied to the container limit: 50% of (limit − 1 GB), with a minimum of 256 MB.
- **Backups:** `mongodump --archive --oplog`.
- **Settings:** server-side JavaScript, off by default.

## Redis

- **ACL users,** in a file generated by Brume and mounted read-only:
  - `default` is disabled;
  - the app can run every command except the administration ones (`CONFIG`, `DEBUG`, `MODULE`, `ACL`, `SHUTDOWN`, `REPLICAOF`, `MONITOR`, `SAVE`, `BGSAVE`, `BGREWRITEAOF`, `SYNC`, `PSYNC`, `FAILOVER`, `MIGRATE`). `INFO` and `CLIENT` stay allowed: libraries such as BullMQ need them;
  - an admin, for Brume;
  - a user limited to `PING`, for the healthcheck.
- **One mode, chosen at creation:**
  - **cache:** no persistence, `allkeys-lru`;
  - **data:** AOF (`appendfsync everysec`) and RDB snapshots, `noeviction`. A queue such as BullMQ or Sidekiq never loses a job to eviction.
- **`maxmemory` at 75% of the container limit:** this leaves room for the fork that writes snapshots.
- **Updates matter more than config.** The October 2025 Lua flaw ([CVE-2025-49844](https://nvd.nist.gov/vuln/detail/CVE-2025-49844)) only needed an authenticated user able to run scripts, and job queues need scripts.
- **Backups:** an RDB snapshot in data mode, none in cache mode.
- **Settings:** `timeout`, for idle connections.

<Callout type="info" title="Open decision: vm.overcommit_memory">
  Redis recommends `vm.overcommit_memory=1` on the host for the fork of its snapshots, but this setting applies to the whole host. Whether Brume sets it is not decided yet.
</Callout>

## Checks at deploy time

Brume checks each database in a throwaway container on the environment network. The container's exit code is its only output. The checks are:

- a connection without a password is refused;
- the app account fails on an admin operation (`CREATE ROLE`, `createUser`, `CONFIG GET`);
- the healthcheck passes.

If a check fails, the deployment fails: the previous version keeps running, or the new database is not marked ready.
