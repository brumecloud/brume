This tutorial takes you from a fresh VPS to an app served on your own domain. You run one command on the server, log it in to your tailnet, open the panel from your laptop, deploy a guestbook made of three public images, and give it a domain.

At the end, your server accepts only SSH and Tailscale from the Internet. You administer it over Tailscale, and public traffic reaches your app through Cloudflare Tunnel.

<Callout type="warn" title="An alpha pre-release">
  This release has no S3 bucket and no backups: Brume's state stays on the server, and a lost server cannot be restored. It does not update itself, signs you in with a one-time link instead of a passkey, and deploys public images only: no builds from GitHub, no templates, no static sites. See [what is not in this release yet](/docs/how-it-works/host-and-installation#not-in-this-release-yet).
</Callout>

## Before you start

- **A fresh VPS** running Ubuntu 24.04 or 26.04, or Debian 12 or 13, on amd64 or arm64. On a server already in use, the ports already published and the services already exposed would stay open. This release was tested on Ubuntu 24.04 on arm64: Debian and amd64 are supported by the code, but not yet tested on a VM.
- **SSH on port 22.** Brume's firewall lets SSH in on port 22 only, so the install refuses an SSH server that listens elsewhere: you would lose access.
- **Access to your hosting provider's console.** It is your way back in if SSH and Tailscale fail. Your account at the host is equivalent to root on the server, so protect it with 2FA.
- **A Tailscale account,** with the device you will use the panel from on your tailnet, and MagicDNS turned on: the panel's address is the server's name on your tailnet.
- **A domain on Cloudflare DNS,** in an account protected by 2FA: it controls your public traffic and all of your domain's DNS, email included. Nothing else may hold the wildcard record `*.<your domain>`: the install points it at the tunnel, and refuses if another record has it.
- **A Cloudflare API token** for that domain, with these permissions: Zone → Zone → Read, Zone → DNS → Edit, Zone → Zone Settings → Edit, and Account → Cloudflare Tunnel → Edit. Create it in Cloudflare's dashboard, under My Profile → API Tokens. The install uses it, then forgets it: it is never written to disk.

You do not install Docker or Tailscale yourself: `brume install` installs both from their official apt repositories.

Know what Cloudflare sees before you start: it decrypts all your public traffic, including your users' passwords and data. It is a US company, which matters for GDPR. See [Networking](/docs/how-it-works/networking#what-it-costs-you).

## Install Brume and deploy an app

<Steps>

<Step>

### Run the install command

On the server, with your domain in place of `example.com`, run:

```bash
curl -sSL https://brume.dev/install.sh | sudo bash -s -- --domain example.com
```

`install.sh` is short enough to read first: `curl -sSL https://brume.dev/install.sh`. It downloads the archive for your server's architecture from the GitHub release, checks it against the SHA-256 written in the script, installs it in `/usr/local/lib/brume`, and runs `brume install` with the same arguments.

`brume install` asks for the Cloudflare API token, and does not echo it. To pass it in the environment instead, set `CLOUDFLARE_API_TOKEN` and keep it through sudo with `sudo --preserve-env=CLOUDFLARE_API_TOKEN`.

Before it changes anything, the install checks the server, and checks that the token has every permission it needs on your domain. If something is missing, it stops and names it. Then it lists its steps and asks you to confirm.

</Step>

<Step>

### Log the server in to your tailnet

The install sets up Brume's firewall and Docker, installs Tailscale, then prints a Tailscale login link and waits. Open it, and log in with your own Tailscale account: the server joins your tailnet as your device.

Your Tailscale login becomes the only one the panel accepts. Nobody becomes admin by connecting to the panel first: the link is printed only in your terminal.

- **If your tailnet requires approving new devices,** the install prints the link to Tailscale's admin console: approve the machine named `brume`.
- **If HTTPS is off in your tailnet,** the install prints the link that turns it on. The panel is served only over HTTPS.
- **The install waits up to 15 minutes,** and prints the link again every 2 minutes. If time runs out, run the same command again: it skips the steps already done.

The install also turns on Tailscale SSH. Your Tailscale identity alone then gives a root shell on the server: this is an accepted risk in alpha 0.1, see the [threat model](/docs/how-it-works/threat-model).

</Step>

<Step>

### Let the install finish

The install then creates one system user per Brume service and starts the services. With your token, it creates a Cloudflare tunnel, points `*.example.com` at it, turns on Always Use HTTPS on the zone, and hands the tunnel to Brume's engine. [Host and installation](/docs/how-it-works/host-and-installation#what-brume-install-does) lists every step.

It ends with the panel's address on your tailnet, `https://brume.<your tailnet>.ts.net`, and a one-time login link. If Cloudflare does not serve your domain yet, the install says so: set Cloudflare's name servers at your registrar.

If a step fails, fix its cause and run the same command again.

</Step>

<Step>

### Open the panel

On your laptop, on your tailnet, open the login link. It works once, within 15 minutes. For a new one, run this on the server:

```bash
sudo brume admin login
```

The panel is reachable only from your tailnet, over HTTPS. `brume api` listens on `127.0.0.1` only, and `tailscale serve` exposes it on your tailnet. Every request must carry your Tailscale login, which Tailscale sets: a request from another login, or from a tagged device, gets a 403. See [Admin panel](/docs/how-it-works/admin-panel).

</Step>

<Step>

### Deploy the guestbook

The guestbook is a web page served by nginx, an API, and Postgres. Its source is in [`examples/demo`](https://github.com/brumecloud/brume/tree/main/examples/demo) of the Brume repository, and its images are public.

In the panel, create a project. In its environment, add a shared variable `POSTGRES_PASSWORD`, as a secret, then add three services, each from an image:

| Slug | Image | Variables | Port | Healthcheck |
|---|---|---|---|---|
| `db` | `postgres:17` | `POSTGRES_PASSWORD`, the shared secret | 5432 | none: the container keeps running |
| `api` | `public.ecr.aws/c6e9e0x1/brume-demo-api:0.2` | `DATABASE_URL`: `postgres://postgres@db:5432/postgres?sslmode=disable`, and `POSTGRES_PASSWORD`, the shared secret | 8080 | `GET /healthz` |
| `web` | `public.ecr.aws/c6e9e0x1/brume-demo-web:0.2` | none | 8080 | `GET /healthz` |

The slugs `db` and `api` matter: the API reaches the database as `db`, and nginx forwards `/api/` to `api`. The data of `db` lives in the volume that `postgres:17` declares, `/var/lib/postgresql/data`, and survives a redeploy.

Deploy. Once the three services are online, open each one: its logs show in the panel.

The three services share the environment's internal network, and none of them can reach your tailnet, your hosting provider's private network or its metadata endpoint. See [Networking](/docs/how-it-works/networking#nftables-rules).

</Step>

<Step>

### Give it a domain

In the settings of `web`, set its public domain to `demo`: the panel completes it with `.example.com`. Deploy, then open `https://demo.example.com`: the page lists the messages, and its form writes to Postgres through the API.

The request goes through Cloudflare, which handles the public certificate, then `cloudflared` and Traefik, to `web`. No port on the server listens for it, and there is no Let's Encrypt or port 80 to manage.

- **One subdomain level,** in the domain of the install: `demo.example.com`, not `demo.apps.example.com`. Cloudflare's free certificate covers `*.example.com` only.
- **The domain belongs to the service,** not to a revision: a rollback neither removes nor brings back a domain.
- **HTTP only.** On Cloudflare's free plan, a request is limited to 100 MB, with a 100-second response timeout.

</Step>

</Steps>

## What you built

- **A server closed to the Internet** except SSH on port 22 and Tailscale. Brume's firewall drops every other inbound connection, and Cloudflare Tunnel works through an outbound connection.
- **A panel reachable only from your tailnet,** for your Tailscale login only.
- **An app made of three containers,** each running as a remapped user, on an internal network that reaches neither your tailnet nor your provider's private network.
- **A public domain** served through Cloudflare Tunnel.

Two things to know while you run this alpha:

- **SSH stays open on port 22.** Brume does not change your SSH server's configuration yet: make sure it accepts keys only.
- **Your server's Tailscale key expires,** like any device's, until Brume tags the server. When it does, the panel is unreachable until the server logs in to Tailscale again. See [Admin panel](/docs/how-it-works/admin-panel#tailscale).
